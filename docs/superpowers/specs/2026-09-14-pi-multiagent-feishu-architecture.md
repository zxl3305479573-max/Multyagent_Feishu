# MultyAgent × 飞书：基于 Pi Agent 的多智能体架构设计

日期：2026-09-14
状态：待评审
前序设计：[2026-09-13-multyagent-feishu-bots-design.md](2026-09-13-multyagent-feishu-bots-design.md)

## 1. 结论先行

关于“六个飞书机器人的 Pi 执行环境是否独立”，答案是：**一套 Pi 安装，六个相互独立的会话与执行边界**。

需要独立、也可以独立的是这四项：

1. 会话上下文（每个机器人一个独立 session）
2. 会话存储目录（每个机器人一个 `sessionDir`）
3. 工作目录（每个机器人一个 cwd，前后端用 git worktree 分开）
4. 工具集与权限（每个机器人一份工具白名单 + 一份策略）

不需要、也不应该独立的是 Pi 的安装本身：CLI、模型凭据、扩展包共享一套，避免六份版本漂移。

必须提前认清的边界：**Pi 不做操作系统级沙箱**。它的设计哲学明确写着“没有权限弹窗——要么跑在容器里，要么用扩展自己实现确认流程”。所以权限不能靠提示词、也不能只靠工具名单，必须有在 `tool_call` 阶段强制拦截的策略扩展。

## 2. 隔离维度对照

| 维度 | 是否独立 | 实现方式 |
| --- | --- | --- |
| 会话上下文 | 独立 | 每个机器人一个 `AgentSession` |
| 会话文件 | 独立 | `--session-dir` / `sessionDir` 分目录 |
| 工作目录 | 独立 | 每个机器人独立 cwd + git worktree |
| 工具集 | 独立 | `tools` 白名单 / CLI `--tools` |
| 模型与思考等级 | 独立 | profile 指定 `--model` `--thinking` |
| 扩展、技能、提示词 | 独立 | 按 session 指定 `--extension` `--skill` |
| 进程 | 可共享可独立 | SDK 单进程多 session，或每机器人一个 RPC 子进程 |
| 操作系统用户 | 默认共享 | 需要容器或独立系统账户才能隔离 |
| 全局设置 | 共享 | `~/.pi/agent/settings.json` |
| 模型 API 凭据 | 共享 | `pi auth` 统一管理 |

## 5. 关键决策：编排归属

这一条决定了整个架构能否成立。

`pi-subagents` 可以让项目经理在自己的 session 内部派生 worker、reviewer 等子 Agent。但如果跨角色协作都在项目经理的内部 session 完成，那么前端、后端、测试的工作结果会由**项目经理机器人**汇报，这与已经确认的规则“谁执行，谁在飞书回复”直接冲突。

因此确定：

- **跨机器人协作由任务编排层负责**。项目经理产出计划后，编排层分别向前端、后端、测试、审计的独立 session 派发任务，各自用各自机器人身份回帖。
- **单个机器人的任务内部**可以自由使用 Pi 的能力，包括 `pi-subagents` 的子 Agent，用于自我复查、并行探索等不改变对外身份的工作。
- 项目经理的 Profile 保留 `subagent` 工具，但它的定位是“自己这一环的深度分析”，不是代替其他机器人发言。

### 5.1 并行执行模型：平级 root session，不是 subagent

六个机器人并行时，它们是**六个平级的 root session**，不是六个 subagent。

| 场景 | 执行单位 | 说明 |
| --- | --- | --- |
| 用户分别 `@` 六个机器人 | 六个独立 root session，各自进程 | 平级、互不隶属、各自一份工具与策略 |
| 同一机器人连续收到多个任务 | 同一 session 串行排队 | Pi 的 session 一次只处理一轮 |
| 某机器人任务内部需要并行 | subagent | 前台或后台子 session，用于自我复查、并行扫描等 |

不能让六个机器人变成项目经理 subagent 的四条硬约束：

1. **身份归属**：子 Agent 的产出回到父 session，由父 Agent 汇报。这和“谁执行谁在飞书回帖”直接冲突。
2. **权限天花板**：`pi-subagents` 的 capability ceiling 是会话级、从父会话继承的，子 Agent 只能更窄、不能更宽。若六个角色都是项目经理的子 Agent，前端和后端就不可能拥有比项目经理更细的独立权限边界。
3. **生命周期**：子 session 绑定父 session，父会话停止子会话随之中止；前台子 Agent 还与父共享同一进程。六个机器人需要能各自独立重启。
4. **上下文**：子 Agent 默认 fork 父会话上下文，六个角色的上下文会互相污染，且不符合“只通过结构化产物传递”的约定。

并行的三种实现方式：

| 方案 | 形态 | 优势 | 代价 |
| --- | --- | --- | --- |
| A | SDK 单进程内六个 `AgentSession` | 内存低，模型运行时只加载一次 | 一个进程崩溃牵连全部；仍是同一系统账户 |
| B | 每个机器人一个长驻 Pi 进程（`--mode rpc`） | 崩溃隔离、独立重启、工具与会话目录天然分离 | 六份进程内存与启动开销 |
| C | 每角色一个容器或独立系统账户 | 真正的强制隔离 | 部署复杂，属于第二阶段 |

**建议采用 B**：Windows 上 `pi-server` 的 Unix socket 传输不可用，RPC 走 stdin/stdout 更合适；同时能用每个进程自己的 `--tools`、`--session-dir`、cwd 和 `--extension` 把边界钉死，日志也天然按机器人分开。若后续内存吃紧，再评估方案 A。

并行时的共享资源冲突需要在编排层处理：

- 同一仓库的并行写入 → 前后端各用独立 git worktree。
- 同一端口、构建缓存、测试数据目录 → 各角色使用独立配置。
- 模型 API 的速率限制 → 编排层设置全局并发上限与退避，不靠各 Agent 自律。

### 5.2 跨 Agent 协作与通信协议

#### 5.2.1 通信原则：星型中介，不做网状直连

六个 Agent 不互相直接发消息。所有跨 Agent 通信都经过编排层这一个中介，形成星型拓扑：

```text
                  编排层（唯一 broker）
        ┌───────────┬───────────┬───────────┐
     项目经理     架构设计师    前端/后端    测试/审计
```

理由有四条：

1. 权限边界只在编排层可校验。点对点直连等于把权限判断交给 Agent 自己。
2. 身份归属不会错乱。谁执行、谁回帖，由编排层的派发记录决定。
3. 可审计。每一条跨 Agent 消息都落库，能还原完整协作链。
4. 可限流、可恢复、可中断。编排层能暂停、取消、重放任意一环。

**需要澄清的是：不直连不等于不通信。** 系统里同时存在两条独立通道：

| 通道 | 承载什么 | 由谁承担 |
| --- | --- | --- |
| 控制面 | 谁该做、下一步派给谁、什么时候唤醒、超时与取消 | 编排层的调度消息与状态机 |
| 数据面 | 交付内容本身（方案、契约、变更、报告） | 共享的产物仓库 |

Agent 依然会“收到消息”，只是发件人是编排层。编排层持有每个机器人的 Pi 会话进程，向目标 session 投入一条结构化任务，就是一次真实的派发动作，目标 Agent 会被唤醒并开始工作。产物文件夹只解决“内容放在哪一版”，它不承担唤醒、顺序、鉴权、幂等和恢复。

反过来说，单靠一个共享文件夹会失效：没有唤醒机制就只能靠轮询，延迟高且空转；没有编排层的校验，前端 Agent 可以随意读取甚至改动后端目录；没有顺序与幂等保证，同一任务会被重复执行；任务中断后也无法知道该从哪一步继续。

所以准确的模型是：**编排层是消息总线与状态机，产物仓库是数据存储；Agent 之间通过编排层交换结构化消息，通过共享仓库交换内容。**

#### 5.2.2 三类消息

跨 Agent 只有三种合法消息，其余一律视为非法：

| 类型 | 方向 | 内容 |
| --- | --- | --- |
| 任务派发 | 编排层 → Agent | 要做什么、验收标准、依赖的产物、截止时间 |
| 产物交付 | Agent → 编排层 | 完成结果与产物引用，不夹带对他人的指令 |
| 澄清请求 | Agent → 编排层 | 缺信息、需决策、发现冲突 |

#### 5.2.3 消息信封

```json
{
  "message_id": "...",
  "task_id": "...",
  "parent_task_id": "...",
  "from": "architect",
  "to": "orchestrator",
  "type": "artifact_delivered",
  "requires": ["contract:api-v1"],
  "artifacts": ["artifacts/api-contract-v1.yaml"],
  "payload_digest": "sha256:...",
  "created_at": "..."
}
```

`payload_digest` 让下游能确认自己读到的是哪一版产物。禁止把大段正文塞进消息体，正文一律以产物文件承载。

#### 5.2.4 产物仓库：协作的真正载体

Agent 之间传递的是产物，不是对话。

```text
runtime/artifacts/<task_id>/
  requirements.md          需求与验收标准
  architecture.md          架构方案
  contracts/api.yaml       接口契约
  contracts/data-model.sql 数据模型
  frontend-change.md       前端变更说明
  backend-change.md        后端变更说明
  test-report.md           测试报告
  audit-report.md          审计报告
  summary.md               项目经理汇总
```

规则：

- 每个 Agent 只写自己的产物文件，不修改他人的产物。
- 产物一旦交付即冻结，修正必须产出新版本并递增版本号。
- 下游读取产物必须记录版本，测试报告要写明基于哪一版契约。

#### 5.2.5 核心规则：先查产物，再派任务

这是防止协作退化成互相提问的关键规则。

当某个 Agent 缺少信息时，它**不是去问另一个 Agent**，而是：

1. 先在产物仓库里查是否已有该产物。
2. 有 → 直接使用，并记录版本。
3. 没有 → 向编排层提交澄清请求。
4. 编排层判断该信息应由谁产出，派发子任务给对应 Agent。
5. 子任务完成、产物落库后，唤醒原任务继续。

举例：前端开发需要接口定义时，不直接问后端开发，而是查 `contracts/api.yaml`。若不存在，编排层派发一个“产出接口契约”的任务给架构设计师或后端开发，完成后前端任务自动恢复。

这样既避免了 Agent 之间的自由对话，也避免了重复提问。

#### 5.2.6 契约是协作的锚点

前后端并行不冲突的前提是契约先行：

```text
架构设计师产出 contracts/api.yaml
      ↓
前端读契约实现调用方
后端读契约实现提供方
      ↓
契约若变更 → 记为显式事件 → 触发受影响方重新验证
```

契约变更不允许静默发生。任何一方发现契约无法满足，都走澄清请求，由编排层决定是修改契约还是调整实现。

#### 5.2.7 典型协作时序

```text
用户 @项目经理 做一个 XX 功能
  ① 项目经理 → 编排层：任务计划（含依赖图）
  ② 编排层 → 架构设计师：产出架构方案与接口契约
  ③ 架构设计师 → 编排层：architecture.md + api.yaml
  ④ 编排层 → 前端开发、后端开发（并行，各自 worktree）
  ⑤ 前端/后端 → 编排层：变更说明 + 自测结果
  ⑥ 编排层 → 测试：基于契约与变更执行验证
  ⑦ 测试 → 编排层：test-report.md
  ⑧ 编排层 → 审计：代码、依赖、权限检查
  ⑨ 审计 → 编排层：audit-report.md
  ⑩ 编排层 → 项目经理：汇总
  ⑪ 项目经理 → 飞书：最终交付
```

每一步在飞书群里都可见，需要人工介入的步骤发审批卡片。

#### 5.2.8 冲突与升级

| 冲突类型 | 处理方式 |
| --- | --- |
| 契约与实现不一致 | 回到契约决策，双方重新验证 |
| 两个 Agent 结论矛盾 | 升级到架构设计师裁决，仍不一致则由人工裁决 |
| 范围外的改动需求 | 升级到项目经理，重新走计划 |
| 高风险动作 | 停止并等待人工审批 |

裁决结果必须写入产物仓库，成为后续任务的依据。

#### 5.2.9 防死循环

跨 Agent 协作必须有硬性上限，否则会出现两个 Agent 互相要求对方先改的僵局：

- 单任务最大派发轮次（建议 8 轮）。
- 单任务最大 Agent 跳转次数（建议 12 次）。
- 同一对 Agent 针对同一议题最多往返 2 次，之后强制升级。
- 依赖图存在环时拒绝执行并报错，不做隐式重试。

#### 5.2.10 与 Pi 原生通信机制的边界

`pi-subagents` 里的 `contact_supervisor`、intercom 属于单 session 内部的父子通信，**只用于机器人内部**，不用于跨机器人。

跨机器人一律走编排层协议。这条边界必须写死，否则很容易出现“前端 Agent 直接给后端 Agent 发消息”的越权路径。

#### 5.2.11 审计

每条跨 Agent 消息记录：发件、收件、类型、关联任务、产物引用、时间、结果。由此可以完整还原“一个需求是怎么被六个 Agent 协作完成的”。

### 5.3 上下文把控

#### 5.3.1 总原则

**上下文的边界 = 权限的边界 = 身份的边界。** 每个 Agent 只持有自己职责所需的最小上下文，既不继承别人的对话，也不共享别人的执行历史。

这既是安全要求（避免 A 的敏感信息经对话泄漏到 B），也是质量要求（避免旧任务的假设污染新任务）。

#### 5.3.2 四层上下文

| 层 | 内容 | 生命周期 | 来源 |
| --- | --- | --- | --- |
| 静态层 | 角色系统提示、项目简述、策略边界声明 | 每个 session 固定 | Profile + `before_agent_start` 注入 |
| 任务层 | 需求、验收标准、依赖产物引用 | 每任务构造一次 | 任务信封 + 产物仓库 |
| 会话层 | 本任务内的对话轮次 | 任务存续期间 | 本 session 自身 |
| 长期层 | 项目记忆、历史产物索引 | 跨任务 | 受控的项目记忆文件 |

关键点是：**任务层靠引用而不是靠复制，会话层不跨任务延续，长期层只读且写入受限。**

#### 5.3.3 会话粒度：一个任务一个 session

机器人身份是长期的，会话是短期的。

- `task_id` 对应一个 session，而不是一个机器人对应一个 session。
- 同一任务内的多轮追问（用户在飞书继续补充）复用同一个 session。
- 新任务开新 session，只注入静态层和该任务需要的产物引用。
- 需要参考历史时，引用产物版本，而不是把旧对话搬过来。

这样做的价值很直接：上下文体积可预测、成本可控、旧任务的错误假设不会漂进新任务、审计时能精确对应到某一个任务。

#### 5.3.4 注入方式：引用优先

| 方式 | 适用场景 | 代价 |
| --- | --- | --- |
| 全量注入 | 小文件、强相关、必须逐字理解 | 昂贵，且稀释注意力 |
| 引用注入（路径 + 摘要 + 版本 + digest） | 默认方式 | 便宜、可控、可追溯 |
| 增量注入（diff） | 修改类任务 | 精准，但依赖基线明确 |

默认走引用注入：告诉 Agent “接口契约在 `contracts/api.yaml`，版本 v3，摘要如下”，由 Agent 用 `repo_read` 自行读取需要的部分。实测比一次性倾倒全文更省、更准。

#### 5.3.5 上下文预算与压缩

- 每个角色设置 token 预算，超出即告警。
- 接近阈值时的正确做法是**把中间结论外置成产物，然后开新 session 继续**，而不是反复压缩旧对话。
- Pi 原生的 `session.compact()` 作为补救手段保留，不作为常规路径，因为压缩会丢失细节且不可逆。
- 单任务轮次上限（见 5.2.9）同时也是一道上下文保护。

#### 5.3.6 敏感信息隔离

- 密钥、令牌、生产配置不允许进入任何 Agent 的上下文。
- 读取文件时经策略层过滤，命中密钥模式则阻断并记录。
- Agent 之间不共享原始对话，只交换结构化消息与产物。
- 审计日志与会话日志中不出现密钥原文。

#### 5.3.7 飞书侧的上下文映射

- 同一个飞书话题内的后续消息 → 关联到同一 `task_id`，复用 session。
- 用户 `@` 另一个机器人 → 默认视为新任务，除非消息中显式引用了任务号。
- 群聊历史不作为上下文来源，飞书只承担入口与展示。

#### 5.3.8 反模式清单

以下做法会导致上下文失控，明确禁止：

1. 六个 Agent 共享同一份对话历史。
2. 把整个仓库塞进上下文。
3. 用对话传递契约，而不落成文件。
4. 无限压缩续跑，而不做上下文外置。
5. 让 Agent 自由读取未授权目录来“补足上下文”。

### 5.4 沟通的落地机制

前面讲了协议，这里讲它到底怎么跑起来。

#### 5.4.1 物理通道只有两条

编排层是一个常驻 Node 进程，同时持有六个 Pi 会话进程（方案 B），每个 Pi 进程一根 stdin / stdout 管道。于是物理上只有两条通道：

| 方向 | 通道 | 载体 |
| --- | --- | --- |
| 下行 | 编排层 → 目标 Pi 进程 stdin | 一行 JSON（`prompt` 命令） |
| 上行 | 目标 Pi 进程 stdout → 编排层 | 一行行 JSON 事件流 |

除此之外没有任何连接。Agent 之间不存在网络连接、消息队列或共享会话。所谓“前端把结果告诉后端”，物理上根本不存在——存在的只有“前端 → 编排层 → 后端”。

#### 5.4.2 一次派发长什么样

编排层写进前端开发进程 stdin 的一行：

```json
{"id":"req-17","type":"prompt","message":"任务 T-42：按 contracts/api.yaml v3 实现登录接口调用方。验收标准见 artifacts/T-42/requirements.md。成果写入 artifacts/T-42/frontend-change.md。"}
```

该进程 stdout 回流的是一串事件，编排层逐行读取：

```json
{"type":"response","id":"req-17","command":"prompt","success":true}
{"type":"turn_start"}
{"type":"tool_execution_start","toolCallId":"call_abc123","toolName":"repo_read","args":{"path":"artifacts/T-42/requirements.md"}}
{"type":"message_update","assistantMessageEvent":{"type":"text_delta","contentIndex":0,"delta":"..."}}
{"type":"tool_execution_end","toolCallId":"call_abc123","toolName":"repo_read","isError":false}
{"type":"turn_end","message":{"...":"..."},"toolResults":["..."]}
{"type":"agent_settled"}
```

一次派发就是一次写 stdin；一次回收就是读 stdout 事件流。

编排层判断“这个 Agent 这一轮彻底结束了”的依据是 `agent_settled`，而不是 `turn_end`。原因是 `agent_end` 之后 Pi 还可能继续自动重试、压缩重试或处理排队消息；只有 `agent_settled` 表示不会再有自动续跑，此时派发下一环才是安全的。这是从 Pi 官方 RPC 协议里确认的行为，不是推测。

#### 5.4.3 上行靠工具，不靠自然语言

Agent 要向外表达事情时，不靠“在回答里写一段话让编排层去猜”，而是调用一个已注册的工具。工具由 `pi-agent-policy` 扩展通过 `pi.registerTool()` 注册，调用即事件，参数被强制校验：

| 工具 | 作用 | 编排层收到后的动作 |
| --- | --- | --- |
| `report_progress` | 报告阶段性进展 | 更新任务状态，可选回帖飞书 |
| `request_input` | 缺信息，需要上游产出 | 查产物仓库，必要时派子任务 |
| `request_approval` | 高风险动作需批准 | 发飞书审批卡片并挂起本轮 |
| `deliver_artifact` | 交付产物 | 校验产物、落库、触发下游 |

工具的实现方式是向编排层暴露的本机回环接口（127.0.0.1 上的专用端口，按任务发放短期令牌）发送一次结构化调用。这样上行是确定的，不依赖模型记得输出特定格式的 JSON。

#### 5.4.4 一次完整往返

```text
① 飞书 @前端开发 → 网关解析 → 创建 T-42
② 编排层写前端进程 stdin：{type:"prompt", message:"任务 T-42 ..."}
③ 前端 Agent 用 repo_read 读契约 → 发现缺少字段
④ 前端调用 request_input("需要 token 过期时间的定义")
⑤ 扩展把请求发到编排层 → 编排层查产物仓库，无此定义
⑥ 编排层写后端进程 stdin：{type:"prompt", message:"补全契约字段并更新 contracts/api.yaml"}
⑦ 后端完成 → deliver_artifact → 编排层校验并落库
⑧ 编排层写前端进程 stdin：{type:"prompt", message:"契约已更新至 v4，请继续"}
⑨ 前端完成 → deliver_artifact("frontend-change.md")
⑩ 编排层按依赖图派发测试任务，并回帖前端机器人告知完成
```

注意第 ⑧ 步：前端进程从头到尾没有被重启，它在第 ④ 步之后处于等待状态，收到新的 prompt 才继续。这就是“挂起与唤醒”，不是轮询。

#### 5.4.5 编排层内部需要维护的东西

| 数据 | 用途 |
| --- | --- |
| 任务表 | task_id、状态、所属 Agent、产物、审批状态 |
| 依赖图 | 谁依赖谁，决定派发顺序与并行分组 |
| 会话映射 | task_id ↔ Pi session 文件，用于恢复 |
| 产物索引 | 产物路径、版本、digest |
| 消息日志 | 每次派发与上行的完整记录 |

SQLite 或结构化 JSON 文件足够。单机六个进程的规模，不需要引入消息队列或中间件——那会把一个可控的本机系统变成需要运维的分布式系统。

#### 5.4.6 一句话总结

下行是编排层写进目标进程 stdin 的结构化任务，上行是 Agent 通过注册工具回调到编排层的结构化事件；中间的一切都记录在任务表与产物仓库里。Agent 之间没有说话，但消息确实在双向流动，只是每一跳都经过编排层。

### 5.5 并行时如何避免冲突

并行不是“同时开六个就完了”，而是要为每一类冲突配上对应机制。

#### 5.5.1 冲突分类与防护

| 冲突类型 | 典型场景 | 防护机制 |
| --- | --- | --- |
| 同文件写入 | 前端与后端改同一个 `package.json` | 单一所有者原则 + 独立 worktree |
| 逻辑不兼容 | 前端按契约 v3 实现，后端已改到 v4 | 契约版本锚定 + digest 校验 |
| 运行时资源抢占 | 两个 Agent 都占用 8080 端口 | 端口、数据库、缓存按工作区隔离 |
| 执行顺序倒置 | 前端在后端产出接口前就开工 | 依赖图决定 blocked / ready |
| 不可并行资源 | 生产部署、数据库迁移 | 全局互斥锁 + 人工审批 |
| 合并冲突 | 两个分支改了同一处代码 | 依赖图排序 + 合并前集成闸门 |
| 模型速率限制 | 六个 Agent 同时请求模型 | 全局并发上限 + 指数退避 |
| 同一机器人多任务 | 两条飞书消息同时到达 | 单机器人串行队列 |

#### 5.5.2 单一所有者原则

每类共享文件只能有一个 Owner，其他人只能提请求，不能直接改：

| 共享文件 | Owner |
| --- | --- |
| `contracts/api.yaml` | 架构设计师 |
| `contracts/data-model.sql` | 架构设计师 |
| 依赖清单（`package.json` 等） | 后端开发 |
| 公共类型定义 | 架构设计师 |
| 构建与部署脚本 | 后端开发 |
| 各角色文档目录 | 各自角色 |

这条规则是解决“改同一文件”的根本办法。只要 Owner 明确，前端和后端就几乎不会碰同一个文件。

#### 5.5.3 乐观并发控制

产物带版本与 digest。Agent 读取时记录版本，写入时校验：

```text
前端读取 contracts/api.yaml v3（digest a1b2…）
后端已把它更新为 v4（digest c3d4…）
前端基于 v3 的写入被拒绝 → 返回“版本冲突，请重新读取”
```

这防止了“基于旧版本默默覆盖新版本”的丢失更新，这是并行系统里最隐蔽也最危险的一类错误。

写入本身也用原子替换（先写临时文件，再 rename），避免读到一个写了一半的文件。

#### 5.5.4 依赖图与阻塞

任务状态里必须有 `blocked` 这一态：依赖未就绪的任务不启动、不空转、不轮询。依赖产物落库后由编排层主动唤醒。

依赖图存在环时直接拒绝执行，不做隐式重试，也不靠 Agent 自行协商。

#### 5.5.5 什么情况必须串行

不是所有环节都该并行，以下情况强制串行：

- 契约尚未确定时，架构必须先行，前后端不得抢跑。
- 存在写依赖的两步改动。
- 涉及不可并行资源（生产环境、数据库迁移、发布）。
- 高风险动作，串行且需审批。

#### 5.5.6 集成闸门

各 worktree 的产物不直接进主干。合并前必须经过一次集成验证：

```text
前端分支 + 后端分支 → 集成分支 → 跑完整测试与构建 → 通过后才允许合并
```

合并顺序由依赖图决定。集成验证失败时，不进入主干，回到对应 Owner 修复。

#### 5.5.7 全局资源闸门

单机六个 Pi 进程各自还会派生 shell 子进程，容易吃满内存与 CPU：

- 全局同时执行的 Agent 数设上限（建议 3，其余排队）。
- 单个 Agent 内部派生 subagent 也设上限。
- 模型请求做全局并发控制与退避，不依赖各 Agent 自律。

#### 5.5.8 冲突发生后的处理

冲突不是让 Agent 自行胡乱合并，而是分类升级：

| 冲突性质 | 处理 |
| --- | --- |
| 契约问题 | 回到架构设计师，产出新版本契约 |
| 实现问题 | 回到对应 Owner 修复 |
| 范围问题 | 回到项目经理，重新走计划 |
| 无法归类 | 暂停任务，交人工裁决 |

受影响的任务在裁决期间一律置为 `blocked`，裁决结果写入产物仓库后才恢复。

### 5.6 git 能约束到什么程度

结论：**git 能可靠解决大约一半的冲突类型，剩下的一半它根本看不到。**

#### 5.6.1 覆盖对照

| 冲突类型 | git 能否解决 | 说明 |
| --- | --- | --- |
| 同文件写入 | 能 | worktree 隔离 + 分支合并时检测 |
| 合并冲突 | 能检测，不能决策 | 能标出冲突位置，但该保留谁的改动需要语义判断 |
| 逻辑不兼容 | **不能** | 改不同文件或不同行时 git 认为干净，运行时才炸 |
| 顺序倒置 | **不能** | git 不知道依赖关系，谁先合并都能过 |
| 运行时资源抢占 | **不能** | 与版本控制无关 |
| 不可并行资源 | **不能** | 部署、迁移不在 git 管辖内 |
| 模型速率限制 | **不能** | 与版本控制无关 |
| 同一机器人多任务 | **不能** | 与版本控制无关 |

git 的本质是**事后、文本级**的检测；并行系统还需要**事前、语义级**的约束。两者是互补关系，不能互相替代。

#### 5.6.2 git 最擅长、也最该交给它做的四件事

1. **隔离**：`git worktree` 让前后端各自拥有独立工作目录，从物理上不可能互相覆盖。
2. **检测**：分支合并时同一区域的双方修改会被明确标出，不会静默覆盖。
3. **闸门**：`pre-commit` / `pre-push` 钩子可以强制跑测试、扫描密钥、校验路径归属。
4. **审计**：每个 commit 带署名与任务号，可完整追溯到哪个 Agent 在哪个任务里改了什么。

#### 5.6.3 git 管不到的核心盲区

最危险的情况是**合并干净但语义已坏**。举例：

```text
后端把 getUser(id) 的签名改成 getUser(id, tenant)
前端在另一处调用了旧签名
两处改动在不同文件、不同行 → git 自动合并成功，无冲突提示
→ 类型检查或测试阶段才暴露
```

git 会认为这次合并完全成功。这类问题只能靠类型检查与集成测试抓住，所以 5.5.6 的集成闸门比 git 的自动合并能力更重要。**自动化验证比自动合并更值得投入。**

#### 5.6.4 具体怎么用 git 约束

| 约束 | 做法 |
| --- | --- |
| 工作区隔离 | 每个写角色一个 worktree + 独立分支 |
| 分支命名 | `agent/<role>/<task_id>`，禁止直接提交到主干 |
| 推送权限 | 策略层只允许 `git_push` 到 `agent/*` 分支，禁止推主干 |
| 合并执行者 | 合并由编排层或人工执行，**不允许 Agent 自行合并** |
| 提交闸门 | `pre-commit` 校验文件归属与密钥扫描 |
| 推送闸门 | `pre-push` 运行对应角色的测试 |
| 生成文件 | 用 `.gitattributes` 排除或指定专用合并策略 |

其中“合并执行者”这条最关键。Agent 可以 commit，可以在自己分支上工作，但把别人的分支合进来这个动作必须由编排层或人来做，否则权限边界形同虚设。

#### 5.6.5 用 git 承担产物版本号

5.5.3 提到的版本与 digest 不必自造一套系统：把契约与产物放进仓库，**直接用 commit hash 作为版本标识**即可。

```text
contracts/api.yaml @ 4f2a9c1  ← 前端实现时锚定这个 commit
后端更新为 @ 8b3d7e5        ← 契约变更成为一次显式提交
测试报告记录“基于 8b3d7e5 验证”
```

好处是三重的：版本天然不可篡改；变更历史可读可回溯；编排层的版本校验直接复用 git 的对象哈希，不需要额外维护版本字段。

#### 5.6.6 冲突检测之后不自动解

git 报出冲突时，**不允许 Agent 自动 resolve**。自动解冲突可能静默丢弃一方的改动，属于高风险动作。

正确流程是：冲突 → 暂停相关任务 → 编排层分类（契约问题 / 实现问题 / 范围问题）→ 升级到对应 Owner 或人工 → 裁决结果落库后再恢复。这与 5.5.8 一致。

### 5.7 交接契约：一个 Agent 完成后该交出什么

交接的质量决定了整条链是否可信。核心原则只有一句：**交出结论与证据，交出产物引用，不交出过程和思考。**

#### 5.7.1 通用交付包（每次必交）

| 字段 | 内容 | 为什么必须有 |
| --- | --- | --- |
| `task_id` / `agent_key` | 任务与执行者 | 身份与追溯 |
| `status` | `completed` / `failed` / `blocked` | 决定编排层下一步 |
| `summary` | 3–10 行结论摘要 | 让下游不必读全文就能判断 |
| `artifacts` | 产物路径 + commit 版本 + digest | 内容载体，可校验 |
| `evidence` | 实际执行的验证命令与结果 | 防“声称通过” |
| `assumptions` | 未经确认的假设（可为空但必须显式声明） | 防隐性假设流向下游 |
| `impact` | 影响的模块、接口、角色 | 决定验证范围 |
| `next` | 建议的下一步与接手者 | 编排层决策参考 |
| `blockers` | 失败时的错误与已尝试路径 | 失败必须可诊断 |

其中 `evidence` 和 `assumptions` 最容易被省略，也最不该省略。证据必须是可复核的命令与输出，而不是"测试通过"这类断言；假设必须显式声明，否则会以隐性前提的形式污染下游判断。

#### 5.7.2 按角色的必交产物

| Agent | 必交产物 | 关键字段 |
| --- | --- | --- |
| 项目经理 | `requirements.md`、`plan.md` | 验收标准、依赖图、责任分配 |
| 架构设计师 | `architecture.md`、`contracts/api.yaml`、`contracts/data-model.sql` | 接口契约版本、技术风险 |
| 前端开发 | `frontend-change.md` + 代码变更 | 变更文件清单、对接的契约版本、构建与自测结果 |
| 后端开发 | `backend-change.md` + 代码变更 | 变更文件清单、接口实现状态、测试结果 |
| 测试 | `test-report.md` | 用例、执行结果、缺陷与复现步骤、覆盖范围 |
| 审计 | `audit-report.md` | 发现（按严重度）、文件与行、依据规则、修复建议 |

#### 5.7.3 谁产出、谁消费

| 产物 | 产出者 | 消费者 |
| --- | --- | --- |
| `requirements.md` / `plan.md` | 项目经理 | 全部角色 |
| `architecture.md` | 架构设计师 | 前端、后端、测试、审计 |
| `contracts/api.yaml` | 架构设计师 | 前端、后端、测试 |
| `frontend-change.md` | 前端开发 | 测试、审计、项目经理 |
| `backend-change.md` | 后端开发 | 测试、审计、项目经理 |
| `test-report.md` | 测试 | 审计、项目经理 |
| `audit-report.md` | 审计 | 项目经理 |
| `summary.md` | 项目经理 | 飞书群与用户 |

产物由产出者独有，消费者只读。测试报告与审计报告一经交付即冻结，修正必须出新版本。

#### 5.7.4 明确不交接的内容

| 不交接 | 原因 |
| --- | --- |
| 完整对话历史与思考过程 | 体积大、噪声高，且泄漏上游上下文 |
| 全量代码 | 用 diff 或文件引用，避免复制失真 |
| 与下一步无关的中间探索 | 稀释注意力 |
| 密钥、令牌、生产配置 | 安全红线 |
| 对他人的指令 | 指挥权只属于编排层，见 5.2.2 |

最后一条尤其重要：Agent 可以建议"建议由后端补齐该字段"，但不能写成"后端去做 XX"。是否派发、派给谁，由编排层决定。

#### 5.7.5 交付包示例

```json
{
  "task_id": "T-42",
  "agent_key": "architect",
  "status": "completed",
  "summary": "完成登录功能架构设计，确定采用 JWT + 刷新令牌方案，定义 4 个接口与 2 张表。",
  "artifacts": [
    { "path": "artifacts/T-42/architecture.md", "commit": "4f2a9c1" },
    { "path": "artifacts/T-42/contracts/api.yaml", "commit": "4f2a9c1", "digest": "sha256:9c1e..." },
    { "path": "artifacts/T-42/contracts/data-model.sql", "commit": "4f2a9c1" }
  ],
  "evidence": [
    { "command": "npx spectral lint contracts/api.yaml", "result": "0 errors, 2 warnings" }
  ],
  "assumptions": [
    "令牌有效期暂定 2 小时，待产品确认",
    "未定义多租户隔离字段"
  ],
  "impact": ["前端登录页", "后端 auth 模块", "测试用例范围"],
  "next": "建议前端与后端基于契约 v1 并行实现，测试随后介入",
  "blockers": []
}
```

#### 5.7.6 编排层如何构造下一步输入

编排层不是把整个交付包丢给下一个 Agent，而是按需抽取：

| 抽取项 | 用途 |
| --- | --- |
| `artifacts` 中与下一步直接相关的部分 | 以引用方式注入（路径 + 摘要 + commit） |
| 验收标准 | 原样传递给执行者 |
| `assumptions` | 转成待确认项，或派任务去确认 |
| `impact` | 决定是否扩大测试与审计范围 |
| `blockers` | 失败时触发升级或重派 |

无关产物一律不注入。前端任务不需要看到审计报告，测试任务不需要看到前端的思考过程。

#### 5.7.7 交付包的校验规则

交付包通过 `deliver_artifact` 工具的 schema 强制校验，**缺字段即视为未完成**，按失败处理，不允许静默通过：

- 产物路径必须真实存在，commit 与 digest 必须可校验。
- `evidence` 不得为空（除非任务本身无验证动作，且需显式说明）。
- `assumptions` 字段必须存在，可以为空数组。
- `status` 为 `failed` 或 `blocked` 时，`blockers` 不得为空。

### 5.8 质量把控的关键要素

多 Agent 系统的质量风险不在“单个 Agent 不够聪明”，而在**没人对整体结果负责**。以下十条是让质量可控的关键。

#### 5.8.1 三条铁律

1. **验收标准先于执行**。没有可执行的验收标准，Agent 只能自己定义“完成”。标准必须由项目经理在派发前给出，且是可判定的。
2. **执行与验证分离**。谁做的谁不验。前端开发的成果由测试独立验证，测试报告不由开发者撰写。
3. **证据必须可复现**。给命令、环境、输出，而不是截图或断言。别人重跑能得到同样结果，才算证据。

这三条不成立，后面所有机制都是空转。

#### 5.8.2 反“表面完成”

Agent 最典型的失败不是做错，而是**声称做了但没做**。以下形态必须在验收时识别并判失败：

| 敷衍形态 | 表现 |
| --- | --- |
| 占位实现 | 函数体是 `TODO` 或空壳 |
| 假实现 | 用 mock 或硬编码绕过困难部分 |
| 改测试而非改实现 | 断言被放宽或测试被注释 |
| 只做局部 | 声明的范围与实际改动不符 |
| 断言过弱 | 测试通过但没验证关键行为 |

对应检查手段：变更必须包含真实文件修改；测试必须真实执行过（且能看到失败先例）；禁止新增未说明的 TODO 与占位符。

#### 5.8.3 对抗性验证

验证者的任务是**证伪，不是确认**。做法：

- 验证 Agent 使用独立 session，不继承执行者的上下文与结论。
- 要求给出反例，或明确说明“尝试了哪些路径仍未能证伪”。
- 禁止“看起来没问题”“应该可以”这类结论。
- 审计 Agent 全程只读，不允许顺手修代码——修复会破坏独立性。

#### 5.8.4 三方一致性

完成的标准不是“某一部分没问题”，而是三方对齐：

```text
契约 ↔ 实现 ↔ 测试
```

契约定义了接口，实现按契约写，测试按契约验。任何一方单独变更都视为未完成。文档与代码同理，术语也必须统一——多个 Agent 对同一概念各用一套说法，是隐性且难以排查的质量杀手，因此需要一份共享术语表。

#### 5.8.5 影响面决定验证范围

交接包里的 `impact` 字段直接决定验证范围：

| 变更范围 | 验证要求 |
| --- | --- |
| 契约或公共接口 | 全量回归 + 测试 + 审计 |
| 单个模块内部实现 | 模块测试 + 相关集成测试 |
| 依赖版本变更 | 依赖审计 + 全量回归 |
| 仅文档 | 一致性检查 |

改了公共接口却只跑局部测试，是并行协作里最常见的质量事故来源。

#### 5.8.6 质量门禁顺序不可跳

```text
实现 → 自测 → 独立测试 → 审计 → 集成验证 → （按需）人审
```

顺序不可调换、不可跳过。任何一环失败都回到对应 Owner，而不是带着问题继续往下走。

#### 5.8.7 预算与停止条件

没有停止条件，Agent 会无限打磨或无限重试：

- 每任务设 token、轮次、时间、成本四项上限。
- 设定质量阈值：达到即停，不追求“更好”。
- 超出预算时不是静默截断，而是标记 `blocked` 并上报。

#### 5.8.8 人审节点要少而关键

人审过多会让系统退化成人工流水线；过少则失去兜底。只审四类：

1. 契约变更。
2. 高风险动作（部署、数据库、权限、推送主干）。
3. 范围变更。
4. 验证未通过但仍需放行的情况。

#### 5.8.9 静默失败一律按失败处理

以下情况是失败，不是通过：

- 任务超时。
- 未产出产物，或产物为空。
- 交付包缺 `evidence`。
- 测试被跳过或未真实执行。
- Agent 直接结束但没有 `deliver_artifact`。

这套系统必须 fail closed：不确定就是不通过，不允许“默认成功”。

#### 5.8.10 可追溯、可回滚、可重放

- 每个结论能追到证据与执行者。
- 每个产物能追到任务与版本。
- 每次变更可回滚。
- 相同输入与上下文可以重放，用于排查回归。

#### 5.8.11 长期质量度量

单次任务通过不代表系统健康。持续跟踪这些指标：

| 指标 | 含义 |
| --- | --- |
| 一次通过率 | 无需返工即通过验收的比例 |
| 返工率 | 需要重派或修复的比例 |
| 缺陷逃逸率 | 通过验收但后续暴露问题的比例 |
| 平均轮次与成本 | 每个任务的效率 |
| 审计发现密度 | 每任务发现的问题数 |

指标恶化时，问题通常出在验收标准、上下文注入或验证独立性上，而不是模型能力。

### 5.9 Agent 之间的协作关系

#### 5.9.1 协作关系图

```text
                    ┌──────────────┐
                    │  项目经理    │ 计划 / 范围 / 汇总
                    └──────┬───────┘
                           │ 验收标准
                    ┌──────▼───────┐
                    │  架构设计师  │ 契约 / 数据模型
                    └──┬────────┬──┘
              契约      │        │      契约
        ┌───────────────▼──┐  ┌──▼───────────────┐
        │   前端开发       │  │   后端开发       │
        └───────┬──────────┘  └──────────┬───────┘
                │  变更说明               │  变更说明
                └───────────┬─────────────┘
                            ▼
                    ┌──────────────┐
                    │   测试       │ 独立验证
                    └──────┬───────┘
                           │ 测试报告
                    ┌──────▼───────┐
                    │   审计       │ 只读检查
                    └──────┬───────┘
                           │ 审计报告
                    ┌──────▼───────┐
                    │  项目经理    │ 汇总回帖飞书
                    └──────────────┘
```

图中每一条边都是**逻辑关系**，物理上全部经编排层转发。

#### 5.9.2 协作矩阵：谁找谁，为了什么

| 发起方 | 接收方 | 目的 | 触发条件 |
| --- | --- | --- | --- |
| 项目经理 | 任一角色 | 派发任务 | 计划确定后 |
| 项目经理 | 架构设计师 | 拿技术方案 | 需求明确、方案缺失 |
| 架构设计师 | 前端 / 后端 | 交付契约 | 契约定稿 |
| 前端 | 后端 | 请求接口定义 | 契约缺字段 |
| 后端 | 前端 | 请求调用约定 | 契约歧义 |
| 前端 / 后端 | 测试 | 交付待验证变更 | 实现完成且自测通过 |
| 测试 | 前端 / 后端 | 回派缺陷 | 验证不通过 |
| 测试 | 架构设计师 | 契约疑问 | 契约与实现矛盾 |
| 审计 | 前端 / 后端 / 测试 | 提出问题 | 发现风险 |
| 任一角色 | 项目经理 | 范围变更 | 超出原计划 |
| 任一角色 | 人工 | 例外裁决 | 无法自动判定 |

注意前端与后端之间的两条：它们不是互相直接对话，而是**通过编排层提出请求**，由编排层判断该由谁产出、是否已有产物。

#### 5.9.3 治理关系：请求权、阻断权、裁决权

协作要能收敛，必须有明确的权力关系，否则会出现“谁都能拦、谁都不负责”。

| 权力 | 持有者 | 作用范围 |
| --- | --- | --- |
| 请求权 | 所有角色 | 通过编排层请求上游补产物或澄清 |
| 阻断权 | 测试 | 验证不通过时阻断流程 |
| 阻断权 | 审计 | 高危发现时阻断流程 |
| 裁决权 | 架构设计师 | 契约与技术方案争议 |
| 裁决权 | 项目经理 | 范围与优先级争议 |
| 裁决权 | 人工 | 例外、裁决权冲突、放行决策 |

关键约束：**阻断权不等于修改权**。测试和审计可以拦下流程，但不能自己改代码，修复必须回到对应 Owner。这样独立性才不会被破坏。

#### 5.9.4 六种协作形态

| 形态 | 适用场景 | 形态说明 |
| --- | --- | --- |
| 接力 | 需求 → 架构 → 实现 → 验证 | 上一环产物是下一环输入 |
| 并行 | 前端与后端 | 无写依赖，基于同一契约同时开工 |
| 汇聚 | 测试汇总两端变更 | 多路输入汇到一处做统一验证 |
| 对抗评审 | 测试、审计 | 目标是证伪，而非确认 |
| 协商 | 契约歧义 | 双方通过编排层交换证据，由裁决者定论 |
| 返修循环 | 缺陷回派 | 修复后重跑，直到通过或升级 |

一次完整任务通常同时用到其中四种：接力 + 并行 + 汇聚 + 对抗评审。

#### 5.9.5 四种典型协作场景

**场景 A：完整功能开发。** 走第 19 章那条主链，串行与并行混合，关键路径是架构 → 前后端 → 测试。

**场景 B：缺陷修复。** 用户直接 `@后端开发` 报缺陷。后端修复并通过自测后，编排层自动派生测试任务做独立验证；若涉及契约，则回到架构确认。修 bug 不必每次都拉上项目经理。

**场景 C：审计发现问题。** 审计产出高危发现 → 阻断流程 → 编排层按问题类型回派 Owner 修复 → 修复后必须由审计复审，不能由修复方自证。

**场景 D：用户直连单角色。** 用户 `@架构设计师` 问一个技术选型问题。此时不需要启动完整流程，架构师直接回答即可。协作有成本，能由一个角色解决的问题不制造协作。

#### 5.9.6 协作的失败模式

| 失败模式 | 表现 | 对策 |
| --- | --- | --- |
| 无限往返 | 两个 Agent 互相要求对方先改 | 轮次与跳转上限，超限强制升级 |
| 责任稀释 | 都参与了，但没人对结果负责 | 每个任务单一 Owner |
| 关键路径过长 | 串行环节堆叠，交付周期被拉长 | 识别关键路径，能并行的并行 |
| 过度升级 | 什么都问人，人审变成流水线 | 明确裁决边界，只审四类 |
| 重复劳动 | 下游重复产出已有产物 | 先查产物再派任务（5.2.5） |
| 隐性假设传播 | 各自按不同前提实现 | `assumptions` 必填并转为待确认项 |
| 协作表演 | 为了让所有角色都出场而制造工作 | 单角色可完成的任务不启动协作 |

最后一条值得强调：多 Agent 的价值在于分工与独立验证，不在于人多。把六个 Agent 都拉进一个本来一个人就能做完的任务，只会增加成本、延迟和出错面。

#### 5.9.7 关键路径

```text
架构 → 前端 ┐
      → 后端 ┴→ 测试 → 审计 → 汇总
```

关键路径上的环节决定整体交付时间。优化顺序应当是先压缩架构与测试的返工，再考虑增加并行度。前后端并行只有在契约稳定时才真正省时间；契约不稳时，并行反而制造返工。

### 5.10 派发契约：下一个 Agent 收到什么

交接契约（5.7）管的是“交出什么”，派发契约管的是“收到什么”。后者决定了下游能否清楚地知道进度、任务、权限与边界。

#### 5.10.1 四块结构

派发包固定由四块组成，正好对应四个必须回答的问题：

| 下游必须清楚的问题 | 对应块 | 内容性质 |
| --- | --- | --- |
| 现在进行到哪一步 | 一、现状 | 动态 |
| 我需要交付什么 | 二、任务 | 动态 |
| 我可以用什么 | 三、权限 | 半静态 |
| 我不能越什么界 | 四、边界 | 静态为主 |

四块缺任何一块都会出问题：缺现状会重复劳动，缺任务会自由发挥，缺权限会畏手畏脚，缺边界会越界。

#### 5.10.2 第一块：现状（进度）

| 字段 | 内容 |
| --- | --- |
| `task_id` / `parent_task_id` | 任务标识与父子关系 |
| `stage` | 当前处于第几环（如 `implementation`） |
| `history` | 已完成环节清单：谁做了什么，一句话结论 |
| `inputs` | 上游产物引用：路径 + commit + digest + 摘要 |
| `verified_facts` | 已被验证的事实（含验证方式） |
| `assumptions` | 上游声明的未确认假设 |
| `ruled_out` | 已失败的尝试与已排除方案 |

两个字段最容易被忽略却最关键：`verified_facts` 让下游不必重新验证已知结论，`ruled_out` 让下游不重复踩坑。没有后者，下一个 Agent 会重新尝试已经失败过的路径。

进度用**阶段清单 + 产物版本**表达，不用对话历史表达。下游要的是“现在在哪”，不是“前面聊了什么”。

#### 5.10.3 第二块：任务

| 字段 | 内容 |
| --- | --- |
| `goal` | 一句话目标，可判定 |
| `deliverables` | 具体交付物：路径、格式、命名 |
| `acceptance` | 验收标准，逐条可判定 |
| `constraints` | 必须遵守的约束（契约版本、接口、命名规范） |
| `definition_of_done` | 完成定义：产物存在 + 证据齐全 + 校验通过 |
| `deadline` / `budget` | 时间与预算 |

`acceptance` 必须可判定。写“代码质量好”是无效标准，写“`npm run test:api` 全绿且新增用例覆盖手机号校验分支”才是。

#### 5.10.4 第三块：权限（可以干什么）

| 字段 | 内容 |
| --- | --- |
| `tools` | 可用工具白名单 |
| `write_paths` | 可写路径 |
| `run_commands` | 可执行命令白名单 |
| `can_request` | 可以向谁请求什么（经编排层） |
| `budget` | token / 轮次 / 时间上限 |

#### 5.10.5 第四块：边界（不越界的部分）

| 字段 | 内容 |
| --- | --- |
| `deny_paths` | 禁止读取或写入的路径 |
| `deny_tools` | 禁止使用的工具 |
| `deny_actions` | 禁止的动作（改契约、改测试、合并分支、部署） |
| `shared_file_owners` | 共享文件归谁所有，自己只能提请求 |
| `escalation` | 遇到边界时该走哪条出口 |

边界必须用**白名单**表达，而不是黑名单。黑名单永远列不全，白名单天然封闭。

`escalation` 这一项是设计上最容易漏、后果最严重的一条。如果不给 Agent 明确出口，它遇到边界时只有两个选择：猜，或者越界。必须显式告诉它：需要额外信息走 `request_input`，需要高风险动作走 `request_approval`，发现冲突走升级。

**给出路比堵路更重要。**

```json
  "constraints": ["契约版本锁定 4f2a9c1", "不得修改契约文件"],
  "definition_of_done": "产物存在 + evidence 齐全 + 交付包校验通过",

  "tools": ["read", "grep", "find", "ls", "repo_read", "repo_write", "run_frontend_tests", "git_diff"],
  "write_paths": ["src/frontend/**", "artifacts/T-42/frontend-change.md"],
  "run_commands": ["npm run test:frontend", "npm run build:frontend"],
  "can_request": ["orchestrator"],

  "deny_paths": ["src/backend/**", "contracts/**", ".env"],
  "deny_tools": ["bash", "powershell", "deploy", "git_push"],
  "deny_actions": ["修改契约", "修改测试用例", "合并分支"],
  "shared_file_owners": { "contracts/api.yaml": "architect", "package.json": "backend-developer" },
  "escalation": {
    "missing_info": "request_input",
    "high_risk_action": "request_approval",
    "conflict": "escalate"
  }

```

#### 5.10.7 如何确保下游真的理解

光把四块发出去还不够，必须有机制保证它被真正执行：

| 机制 | 作用 |
| --- | --- |
| 结构固定 | 四块字段固定，不靠自然语言自由描述 |
| 分层注入 | 角色与边界走系统提示，进度与任务走任务信封 |
| 双通道 | 提示词告知，策略层强制拦截，二者一致 |
| 开工复述 | 首次工具调用前，要求复述目标、交付物、写权限、禁止项 |
| 首次越界即失败 | 被策略层拦下即标记违规并上报，不静默重试 |
| 明确出口 | 缺信息与高风险动作都有指定出口，逼它走正门 |
| 白名单边界 | 只列“可做什么”，不列“不可做什么” |

其中“开工复述”是性价比最高的一条：让 Agent 在动工前用自己的话复述一遍目标、交付物、自己的写权限范围和它认为的禁止项，编排层比对派发包，不一致就重新派发。一次复述的成本，远低于方向跑偏后返工的成本。

#### 5.10.8 三层防护

边界在三个层次上同时生效，任何一层单独使用都不够：

| 层次 | 承担什么 | 是否强制 |
| --- | --- | --- |
| 系统提示 | 角色定位、职责范围、交付规范 | 否，属告知 |
| 任务信封 | 本次任务的权限、写路径、禁止项 | 否，属告知 |
| 策略层 `tool_call` | 路径、命令、工具的实时校验 | **是，可阻断** |

只做前两层，等于把边界交给模型自觉；只做第三层，模型会反复尝试再被拦下，效率低且容易误判。三层一致，下游才既知道边界，又越不过边界。

### 5.11 成本控制：token 花在哪里，怎么降

#### 5.11.1 成本结构

多 Agent 系统的 token 消耗近似于：

```text
总成本 ≈ Σ(轮次 × 每轮上下文长度)
```

每轮上下文 = 系统提示 + 工具定义 + 会话历史 + 注入的产物。三个来源：

| 来源 | 特征 | 放大方式 |
| --- | --- | --- |
| 固定开销 | 系统提示、工具 schema | 随轮次线性放大 |
| 会话历史 | 本任务此前的所有轮次 | 随轮次近似平方放大 |
| 产物注入 | 上游产物正文 | 随参与的 Agent 数线性放大 |

#### 5.11.2 关键认知：轮次是主因

成本的主因不是“Agent 多”，而是**轮次多**。因为每一轮都要把系统提示、工具定义和全部历史重新发一次——第 30 轮的成本里包含了前 29 轮的全部内容。

所以降成本的两个有效杠杆是：

1. **减少轮次**。
2. **压缩每轮上下文**。

而“砍 Agent 数量”是错误方向：砍掉测试或审计省下的钱，会以质量事故的形式还回去，且返工成本远高于省下的 token。

#### 5.11.3 任务分级：最大的成本杠杆

不是所有任务都该走完整链路。按影响面分级派发：

| 级别 | 场景 | 参与者 | 产物 |
| --- | --- | --- | --- |
| L0 | 技术问答、方案咨询 | 单个角色 | 无，直接回答 |
| L1 | 单文件小改动 | 单个角色 + 自测 | 变更说明 |
| L2 | 单模块改动 | 1–2 个角色 + 测试 | 变更说明 + 测试报告 |
| L3 | 跨模块或契约变更 | 完整链路 | 全套产物 |

实际项目中绝大多数请求应落在 L0/L1。第 19 章那条完整链路只用于 L3。这一条的分流效果，比任何单点优化都大。

#### 5.11.4 十项降本措施

| 措施 | 省在哪 | 是否牺牲质量 |
| --- | --- | --- |
| 任务分级 | 减少无谓的参与者与轮次 | 否 |
| 引用注入 | 产物正文只读一次，不再层层复制 | 否 |
| 产物摘要 ≤200 token | 下游先读摘要，需要细节再读全文 | 否 |
| 一任务一 session | 避免历史跨任务累积 | 否 |
| 中间结论外置后新开 session | 避免长历史的平方级放大 | 否 |
| 限制每角色工具数量 | 工具 schema 每轮都发，少即是省 | 否，且更安全 |
| 只给直接依赖 | 无关产物不注入 | 否 |
| 确定性工具替代 LLM | lint、类型检查、依赖扫描、覆盖率用命令跑 | 否，且更可靠 |
| 差分代替全量 | 测试与审计看 diff，不看全库 | 否 |
| 模型分级 | 摘要、路由、格式转换用小模型 | 否 |

其中“确定性工具替代 LLM”收益最大：让 Agent 跑 `npm audit` 而不是读完整个依赖树自己判断，既省 token 也更准确。

#### 5.11.5 提示词组织与缓存

多数模型提供方支持提示词缓存，命中的输入 token 价格显著更低。命中的前提是**前缀稳定**：

```text
[稳定] 系统提示 → 工具定义 → 角色边界
[变化] 任务信封 → 产物引用 → 本轮追问
```

所以组织上下文时必须有纪律：静态内容放最前且不要改动，动态内容放最后。把时间戳、随机 ID、本次任务描述混进系统提示，会让缓存永远失效——这是很常见也很贵的错误。

#### 5.11.6 成本可观测

Pi 的事件流里带 `usage` 字段，编排层按任务累计并记录：

| 记录项 | 用途 |
| --- | --- |
| 每任务 token 与成本 | 定位昂贵任务 |
| 每角色平均轮次 | 发现低效角色 |
| 缓存命中率 | 验证前缀稳定性 |
| 返工消耗占比 | 衡量质量对成本的影响 |

没有这层观测，降本只能靠猜。

#### 5.11.7 预算与降级

- 每任务设 token 上限，接近阈值时先告警，再强制外置结论。
- 超限时不是静默截断，而是标记 `blocked` 上报。
- 长任务拆成多个短 session，而不是让一个 session 无限拉长。

#### 5.11.8 不能为省成本砍掉的东西

以下三项是质量底线，任何情况下不因成本妥协：

1. 独立验证（测试不复用开发者的结论）。
2. 审计的只读独立性。
3. 证据的可复现性。

成本优化应该作用在轮次、上下文体积和参与者数量上，而不是作用在验证环节上。

### 5.12 六个机器人的流转序列（时序视图）

5.9 讲的是「谁和谁有关系」，这里讲「球是怎么传的」。

#### 5.12.1 主链流转

| 序 | 当前持有者 | 完成动作 | 流转给 | 传递内容 |
| --- | --- | --- | --- | --- |
| 1 | 用户 | 在群里提出需求 | 项目经理 | 原始需求 |
| 2 | 项目经理 | 拆解、定验收标准 | 架构设计师 | 需求文档引用 + 验收标准 |
| 3 | 架构设计师 | 出方案与契约 | 前端 + 后端（并行） | 契约引用 + 版本 + 约束 |
| 4 | 前端 / 后端 | 各自实现并自测 | 测试 | 变更说明 + 契约版本 + 自测证据 |
| 5 | 测试 | 独立验证 | 审计 | 测试报告 + 变更引用 |
| 6 | 审计 | 只读检查 | 项目经理 | 审计报告 |
| 7 | 项目经理 | 汇总交付 | 飞书群 | 交付摘要 + 产物链接 |

每一步的“完成动作”一旦产出了符合交接契约的交付包，才触发下一跳。没有交付包就不流转。

#### 5.12.2 关键点：回帖归属与流转不是同一件事

流转是**任务**在移动，回帖是**身份**在发言。两者必须分清：

| 环节 | 谁在群里发言 |
| --- | --- |
| 用户提出需求 | 用户 |
| 项目经理完成计划 | 项目经理机器人 |
| 架构设计师完成契约 | 架构设计师机器人 |
| 前端完成实现 | 前端机器人 |
| 后端完成实现 | 后端机器人 |
| 测试完成验证 | 测试机器人 |
| 审计完成检查 | 审计机器人 |
| 最终汇总 | 项目经理机器人 |

所以群里看到的是一串交替出现的发言，每个机器人都只为自己完成的那一环说话。

#### 5.12.3 分支流转

主链之外的流转都发生在异常或返修场景：

| 触发 | 从 | 到 | 目的 |
| --- | --- | --- | --- |
| 验证不通过 | 测试 | 前端 / 后端 | 回派缺陷修复 |
| 契约与实现矛盾 | 测试 | 架构设计师 | 契约澄清或修正 |
| 发现安全或质量问题 | 审计 | 对应 Owner | 回派修复（审计自身只读） |
| 验证覆盖不足 | 审计 | 测试 | 要求补充验证 |
| 契约缺字段 | 前端 / 后端 | 编排层 → 契约 Owner | 补齐契约后再继续 |
| 超出原计划 | 任一角色 | 项目经理 | 范围重新评估 |
| 无法自动判定 | 任一角色 | 人工 | 例外裁决 |

注意第五行：前端需要契约补充时，**不是流转给后端，而是流转给编排层**，由编排层判断该由谁产出。前端与后端之间没有直接的流转边。

#### 5.12.4 返修循环与终止条件

返修是唯一会形成环的流转：

```text
测试发现缺陷 → 回派前端/后端 → 修复 → 重新验证
                    ↑                    │
                    └──── 未通过 ────────┘
```

必须有硬性终止条件，否则会无限循环：

| 条件 | 动作 |
| --- | --- |
| 同一缺陷返修超过 2 次 | 强制升级，交人工裁决 |
| 单任务 Agent 跳转超过 12 次 | 暂停并上报 |
| 单任务派发轮次超过 8 轮 | 暂停并上报 |
| 修复后复审仍失败且原因相同 | 判定为契约或需求问题，回到架构或项目经理 |

#### 5.12.5 三类禁止的流转

| 禁止 | 原因 |
| --- | --- |
| 前端直接流转给后端 | 绕过编排层，权限与审计同时失效 |
| 跳过测试直接进审计 | 独立验证被跳过，质量失守 |
| 审计直接改代码再流转 | 审计失去只读独立性 |

这三条不靠自觉，由策略层与编排层的路由规则强制。

#### 5.12.6 一次完整任务在飞书里的发言顺序

```text
用户            @项目经理 做一个手机号登录
项目经理机器人   计划：4 个环节，先出契约
架构设计师机器人  契约 v1 已定稿，含 4 接口 2 表（待确认）
用户            确认
前端机器人       前端实现完成，测试 42 项通过
后端机器人       后端实现完成，接口自测通过
测试机器人       验证完成，发现 1 个缺陷已回派
后端机器人       缺陷已修复，重新验证通过
测试机器人       复验通过，测试报告已交付
审计机器人       未发现高危问题，2 项建议已列出
项目经理机器人    全部完成，交付摘要如下……
```

这条发言序列就是整条流转链在群里的投影。看清谁在什么时候说话，就能判断任务停在了哪一环。

### 5.13 依赖关系由谁给出

#### 5.13.1 一句话结论

**项目经理提案，编排层持有并校验，运行期的新增依赖由编排层推导。Agent 自己没有连边的权力。**

#### 5.13.2 分层来源

| 依赖类型 | 谁给出 | 何时 |
| --- | --- | --- |
| 任务顺序依赖（谁先谁后） | 项目经理 | 计划期，写在 `plan.md` 的依赖图里 |
| 接口与契约依赖 | 架构设计师 | 契约定稿时隐含确定 |
| 数据模型依赖 | 架构设计师 | 数据模型定稿时 |
| 验证依赖（谁必须验谁） | 编排层按固定门禁推断 | 不需要任何角色声明 |
| 运行期新增依赖 | Agent 提澄清请求 → 编排层推导 | 执行过程中 |
| 依赖冲突或成环 | 编排层检测 → 升级裁决 | 校验时 |

所以“依赖关系”不是一份由某个 Agent 独自维护的清单，而是**一个由编排层持有的图**，不同阶段有不同的输入来源。

#### 5.13.3 为什么 Agent 不能自己连边

如果前端 Agent 能直接声明“我依赖后端”，它实际上就掌握了路由权——决定谁先做、谁等谁、要不要插入新任务。这和 5.2 的星型中介原则冲突：路由权只在编排层。

所以 Agent 只能表达**需求**，不能表达**依赖**：

| Agent 可以写 | Agent 不可以写 |
| --- | --- |
| “需要令牌过期时间的定义” | “等后端补完契约我再继续” |
| “当前缺少 X 才能完成 Y” | “先让架构师改契约” |

编排层收到需求后，判断该由谁产出，再决定是否新增一条依赖边。

#### 5.13.4 依赖的表示与满足判定

依赖以任务为粒度，不细到文件：

```json
{ "task_id": "T-42-frontend", "depends_on": ["T-42-contract"] }
```

一条依赖被判定为**满足**，需要同时具备三个条件：

1. 被依赖任务的产物已交付并通过交接包校验。
2. 产物版本与 digest 可验证。
3. 被依赖任务状态为 `completed`。

三者缺一，下游保持 `blocked`，不启动、不空转。

#### 5.13.5 哪些依赖不需要声明

质量门禁的顺序是固定的，属于编排层的内置规则，不需要项目经理在依赖图里写：

```text
实现 → 自测 → 独立测试 → 审计 → 集成验证
```

这样能显著减轻计划负担：项目经理只需要描述**业务上的先后关系**，流程性的先后由编排层保证。

#### 5.13.6 依赖变更怎么处理

| 场景 | 处理 |
| --- | --- |
| 范围变更导致依赖变化 | 回项目经理重新出计划 |
| 契约变更导致依赖变化 | 编排层按 `impact` 重算受影响任务 |
| 执行中发现新依赖 | 澄清请求 → 编排层新增边并派发 |
| 检测到环 | 拒绝执行，升级人工 |
| 被依赖任务失败 | 下游保持 `blocked` 并上报，不自动跳过 |

最后一条尤其要注意：**依赖失败不能静默跳过**。否则下游会基于不存在的产物继续工作，产出的东西看似通过、实则建立在错误前提上。

## 6. 角色 Agent Profile

Profile 用 Markdown + YAML frontmatter 定义，放在项目级目录，随项目走：`<项目>\.pi\agents\<name>.md`。

```markdown
---
name: architect
description: 系统架构设计、模块边界、技术选型与接口规范
thinking: high
systemPromptMode: replace
tools: read, grep, find, ls, repo_read, doc_write
---

你是架构设计师……（职责、边界、交付格式）
```

六个 Profile 的定位：

| Agent | name | 职责 | 交付物 |
| --- | --- | --- | --- |
| 项目经理 | `project-manager` | 拆解目标、编排、跟进、汇总 | 任务计划、进度、交付汇总 |
| 架构设计师 | `architect` | 架构、模块边界、接口、技术风险 | 架构方案、接口契约 |
| 前端开发 | `frontend-developer` | 页面、组件、交互、样式 | 代码变更、构建结果 |
| 后端开发 | `backend-developer` | 接口、业务逻辑、数据模型 | 代码变更、接口实现 |
| 测试 | `tester` | 测试设计、执行、缺陷、回归 | 测试报告、缺陷清单 |
| 审计 | `auditor` | 代码质量、安全、依赖、权限 | 审计报告、风险清单 |

Profile 里的 `tools` 只是“模型可见的工具”，不等于强制权限。强制权限在策略扩展里。

## 7. 工具设计

### 7.1 内置工具

可用内置工具：`read`、`write`、`edit`、`grep`、`find`、`ls`、`bash`、`powershell`。

其中 `bash` 和 `powershell` 无法按参数限制。给了就等于给了该账户的全部本机能力。所以：

- 只读角色（架构、测试、审计）：给 `read, grep, find, ls`，不给 shell。
- 写角色（前端、后端）：给 `read, grep, find, ls, edit, write`，再加受控的执行工具。
- 项目经理：给读取类工具 + 编排类工具，不给写。

### 7.2 受控工具的实现方式

Pi 的原生思路是“用 CLI 工具 + README 做技能，或用扩展注册工具”。因此不引入 MCP，而是做一个本地扩展 `pi-agent-policy`，通过 `pi.registerTool()` 注册角色专属工具：

| 工具 | 作用 | 风险 | 审批 |
| --- | --- | --- | --- |
| `repo_read` | 按路径读取仓库文件 | 低 | 否 |
| `repo_search` | 限定范围检索 | 低 | 否 |
| `repo_write` | 按路径写入，受路径白名单约束 | 中 | 否 |
| `git_diff` | 查看变更 | 低 | 否 |
| `run_frontend_tests` | 执行前端测试命令 | 中 | 否 |
| `run_backend_tests` | 执行后端测试命令 | 中 | 否 |
| `run_test_suite` | 执行白名单测试套件 | 中 | 否 |
| `dependency_audit` | 依赖与漏洞扫描 | 低 | 否 |
| `secret_scan` | 密钥与敏感信息扫描 | 低 | 否 |
| `deploy` | 部署 | 高 | 是 |
| `db_migrate` | 数据库变更 | 高 | 是 |
| `git_push` | 推送远端 | 高 | 是 |

每个工具声明五项：名称、输入 schema、风险等级、是否需审批、允许操作的路径或命令范围。模型看到的是工具名，策略扩展看到的是参数，两者配合才能既可用又可控。

## 8. 权限矩阵

| Agent | 读取 | 写入 | 执行 | 明确禁止 |
| --- | --- | --- | --- | --- |
| 项目经理 | 全仓库只读 | 仅任务与计划文档 | 不允许 | 改代码、部署、推送 |
| 架构设计师 | 全仓库只读 | 仅 `docs/architecture/` | 不允许 | 改业务代码 |
| 前端开发 | 前端目录 + 接口契约 | 仅前端目录 | 前端测试命令 | 后端目录、数据库、部署 |
| 后端开发 | 后端目录 + 接口契约 | 仅后端目录 | 后端测试命令 | 前端目录、生产数据库、部署 |
| 测试 | 全仓库只读 | 仅测试报告 | 白名单测试套件 | 修改业务代码 |
| 审计 | 全仓库只读 | 仅审计报告 | 只读扫描类命令 | 任何写入或修复动作 |

高风险动作（部署、数据库变更、推送、权限修改、批量删除）一律进入审批，不允许 Agent 自行决定。

## 9. 权限强制执行

这是整套设计里唯一不能妥协的部分。实现为 Pi 扩展 `pi-agent-policy`：

1. 订阅 `tool_call` 事件，在工具真正执行前拿到工具名与参数。
2. 读取该 Agent 的策略文件，检查路径、命令、风险等级。
3. 违规时返回 `{ block: true, reason }`，工具不执行，原因回传给模型。
4. 需要审批时，写入待审批队列并终止本轮，由编排层发飞书审批卡片。
5. 所有判断写入审计日志，包含时间、Agent、工具、参数摘要、结论。
6. 通过 `before_agent_start` 注入当前 Agent 的边界声明，让模型提前知道限制，减少无效尝试。

策略文件示例：

```yaml
agent: frontend-developer
allow_paths:
  - src/frontend/**
  - docs/frontend/**
allow_commands:
  - npm run test:frontend
  - npm run build:frontend
deny_paths:
  - src/backend/**
  - .env
approval_required:
  - deploy
  - git_push
```

`tool_call` 是同步阻塞点，因此拦截是强制的；模型无法通过换个说法绕过。

## 10. 工作区隔离

前端和后端如果在同一个工作目录里并行改代码，会互相踩踏。使用 git worktree 给每个写角色一个独立工作树：

只读角色（架构、测试、审计）可以共用主仓库目录，但通过策略限制为只读。

## 11. 会话与任务状态


状态机：

```text
                              ↓

```

会话策略：机器人身份常驻，会话按任务划分（详见 5.3.3）。同一机器人一次只执行一个任务，其余排队；同一任务的多轮追问复用同一 session，新任务开新 session。跨机器人不共享对话历史，只通过结构化产物传递（架构方案、接口契约、变更清单、测试报告、审计报告）。

## 12. 飞书映射与消息流

```text
飞书 App ID → agent_key → Agent Profile → Pi session → 工作区 → 策略文件
```

单机器人任务：

```text
@前端开发 实现登录页
  → 网关识别 app_id → frontend_developer
  → 登记 task_id，回执“已接收”
  → 向前端 session 发 prompt
  → 事件流写入日志与任务状态
  → 完成后由「前端开发机器人」发送结果
```

跨角色协作：

```text
@项目经理 做一个 XX 功能
  → 项目经理 session 产出计划
  → 编排层按计划分别派发给架构 / 前端 / 后端 / 测试 / 审计
  → 每个角色完成后由各自的机器人回帖
  → 项目经理机器人最终汇总
```

### 12.1 回流飞书的三类消息

| 类型 | 时机 | 内容 | 频率控制 |
| --- | --- | --- | --- |
| 接收回执 | 收到任务后秒级 | 任务号、已接收、预计耗时 | 每任务一条 |
| 状态更新 | 关键节点 | 开始执行、等待审批、缺信息、阻塞 | 同一卡片更新，不刷屏 |
| 最终结果 | 任务结束 | 结论、产物、证据、待办 | 每任务一条 |

关键做法：**状态更新不新发消息，而是更新同一张任务卡片。** 飞书支持卡片消息的原地更新，一张卡片从“处理中”变成“已完成”，群聊不会被过程日志淹没，成员随时能查到当前状态。

### 12.2 最终结果卡片的结构

按重要性排序，前两项必须一眼可判：

| 区块 | 内容 | 长度 |
| --- | --- | --- |
| 状态与结论 | 完成 / 失败 / 阻塞 / 待审批 + 一句话结论 | 1 行 |
| 任务标识 | `T-42`、执行角色、耗时 | 1 行 |
| 交付物 | 产物路径 + 版本（commit）+ 链接 | 列表 |
| 验证证据 | 跑了什么、结果如何 | 1–3 行 |
| 影响面 | 涉及的模块、接口、角色 | 1–2 行 |
| 需要人处理 | 待确认项、待审批、后续建议 | 有则显示 |

示例：

```text
✅ 已完成：手机号登录前端实现
T-42 · 前端开发 · 耗时 6 分钟

交付物
  src/frontend/auth/**            @ a1b2c3d
  artifacts/T-42/frontend-change.md @ a1b2c3d

验证
  npm run test:frontend  42 passed
  npm run build:frontend success

影响面
  新增 /auth/phone 路由，对接 contracts/api.yaml @ 4f2a9c1

需要处理
  令牌有效期暂定 2 小时，待产品确认
```

### 12.3 各角色回帖的差异

因为“谁执行谁回帖”，每个角色的回帖主体不同：

| 角色 | 回帖主体内容 |
| --- | --- |
| 项目经理 | 计划摘要、依赖关系、最终交付汇总 |
| 架构设计师 | 方案要点、契约链接、技术风险与假设 |
| 前端开发 | 变更清单、构建结果、对接的契约版本 |
| 后端开发 | 变更清单、接口实现状态、测试结果 |
| 测试 | 用例数、通过率、缺陷清单、覆盖范围 |
| 审计 | 发现按严重度、涉及文件与行、修复建议 |

失败与阻塞时的回帖比成功时更重要，必须包含三件事：失败在哪一步、原因是什么、需要谁做什么。缺少任何一件，人就要重新追问一轮。

### 12.4 长内容如何处理

飞书消息有长度限制，长内容一律外置：

| 内容 | 处理方式 |
| --- | --- |
| 完整方案、报告 | 写入产物文件，消息里给路径与摘要 |
| 代码变更 | 给 diff 摘要与 commit，不贴全文 |
| 测试日志 | 给结论与失败摘要，完整日志留在产物目录 |
| 大体积产物 | 上传飞书云文档或附件，给链接 |

原则：**消息里只放能让人做判断的最小信息，细节靠链接。**

### 12.5 不回流飞书的内容

| 不返回 | 原因 |
| --- | --- |
| 模型的思考过程与推理细节 | 噪声大，且可能含敏感推导 |
| 完整会话日志 | 体积大，应留在日志系统 |
| 密钥、令牌、连接串 | 安全红线，任何条件下不出现 |
| 对其他 Agent 的指令 | 指挥权只属于编排层 |
| 逐条工具调用记录 | 群里有价值的是结论，不是过程 |

### 12.6 线程与节流

- 同一任务的所有消息挂在同一条话题线程下，避免多个任务在群里交错。
- 状态更新做节流：同一任务在短时间内的多次变化合并为一次卡片更新。
- 若执行时间较长，设置一个“仍在进行”的心跳，但间隔不小于 1 分钟。
- 审批卡片单独成条，确保不被状态更新淹没。

### 12.7 追问与新任务的区分

- 同一线程内的追问 → 复用同一 `task_id` 与会话，连续上下文。
- `@` 另一个机器人 → 默认新任务，除非消息里显式引用任务号。
- 引用任务号跨角色追问 → 由编排层路由到原任务，不新建。

### 12.8 实时任务看板（多维表格）

可行，而且飞书已有现成载体：**多维表格（Bitable）**。它本质上是一个可被 API 读写的在线数据库，天然支持分组、筛选、多种视图和实时协作查看。

#### 12.8.1 与消息卡片的分工

| 载体 | 承载 | 特点 |
| --- | --- | --- |
| 任务卡片 | 单个任务的进度 | 原地更新，适合跟踪一个任务 |
| 多维表格 | 全部任务的全局视图 | 适合回答“现在谁在干嘛、接下来做什么、完成了什么” |

两者互补：卡片让人看到某件事的进展，表格让人看到全局。

#### 12.8.2 主表字段设计

一张「任务看板」表即可覆盖三个问题：

| 字段 | 类型 | 回答的问题 |
| --- | --- | --- |
| `task_id` | 文本 | 标识 |
| `parent_task_id` | 文本 | 子任务归属 |
| `title` | 文本 | 在做什么 |
| `agent` | 单选 | 谁在做 |
| `stage` | 单选 | 当前处于哪一环 |
| `status` | 单选 | `queued` / `running` / `blocked` / `awaiting_approval` / `completed` / `failed` |
| `progress` | 数字 | 粗略进度百分比 |
| `depends_on` | 关联 | 未来被谁阻塞 |
| `artifacts` | 链接 | 产物位置 |
| `blocker` | 文本 | 阻塞原因 |
| `owner_action` | 文本 | 需要谁处理 |
| `started_at` / `updated_at` / `finished_at` | 日期 | 时间线 |
| `tokens` | 数字 | 成本（可选） |

三个问题分别由不同字段组合回答：

- **现在在干嘛** → 筛选 `status = running`，看 `agent` 与 `stage`。
- **未来需要干嘛** → 筛选 `status ∈ {queued, blocked, awaiting_approval}`，看 `depends_on`。
- **完成了什么** → 筛选 `status = completed`，按 `finished_at` 倒序。

注意“未来要做什么”不需要单独维护一份清单——它本来就是编排层依赖图里的未执行节点，直接同步即可。

#### 12.8.3 第二张表：Agent 状态

| 字段 | 类型 |
| --- | --- |
| `agent` | 单选 |
| `state` | 单选：空闲 / 执行中 / 阻塞 |
| `current_task` | 关联到主表 |
| `today_completed` | 数字 |
| `today_tokens` | 数字 |

这张表能一眼看出哪个 Agent 是瓶颈，也为 5.11.6 的成本观测提供界面。

#### 12.8.4 视图设计

| 视图 | 配置 | 用途 |
| --- | --- | --- |
| 全局看板 | 按 `status` 分组 | 日常总览 |
| 按 Agent 分组 | 按 `agent` 分组 | 看每个角色的负载 |
| 我关注的 | 按任务标识筛选 | 发起人跟踪自己提的需求 |
| 已完成 | `status = completed`，按时间倒序 | 交付记录 |
| 待我处理 | `owner_action` 非空 | 审批与待确认项 |

#### 12.8.5 数据来源与更新时机

数据不在飞书侧维护，而是**单向同步**：编排层的任务表是唯一事实来源，飞书表格只是它的投影。

更新时机只有状态变更事件：任务创建、开始执行、进入阻塞、进入待审批、完成、失败。不做轮询式刷新。

#### 12.8.6 实时性与限流

- 飞书开放接口有频率限制，因此必须做写队列与合并：同一记录短时间内的多次变更合并为一次更新。
- 只更新变化的记录，不重建整表。
- 更新失败要重试并记录；连续失败时降级为消息卡片，并在系统告警里提示。
- 表格记录规模建议控制在数千条内，历史任务定期归档到另一张表。

#### 12.8.7 权限

只需要**一个应用**拥有多维表格的读写权限，由编排层使用。六个角色机器人不需要开通该权限——它们只负责各自的消息回帖。

这符合最小权限原则：表格是系统状态，不是某个角色的业务输出。

#### 12.8.8 降级方案

若多维表格不可用（权限未批、接口异常、频率超限），退化为：

1. 群内一张「任务总览卡片」，由编排层定时原地更新。
2. 保持每个任务卡片正常更新。
3. 系统告警中提示看板数据延迟。

看板是观测手段，不应成为流程的单点依赖——它挂了，任务照常流转。

### 12.9 多维表格的配置清单

即使消息权限已经配好，多维表格仍需要单独开通与授权。以下按顺序核对。

#### 12.9.1 开通 API 权限

在开放平台「权限管理」中搜索“多维表格”，后台实际提供两条：

| 后台显示名称 | 权限标识 | 是否需审核 | 看板场景 |
| --- | --- | --- | --- |
| 查看、评论、编辑和管理多维表格 | `bitable:app` | 免审权限 | **需要，选这一条** |
| 查看、评论和导出多维表格 | `bitable:app:readonly` | — | 不够，只能查看与导出，写不了记录 |

因为看板需要创建与更新记录，必须选择 `bitable:app`。它是免审权限，添加后无需等待管理员审批。

添加后仍需**创建新版本并发布**，权限才会对线上生效——这一点与消息权限一致。

#### 12.9.2 最容易漏的一步：把应用加为表格协作者

这是最常见的失败原因。API 权限开通后，应用仍然需要被授权访问**那一张具体的表**：

1. 打开目标多维表格。
2. 右上角「分享」或「协作」。
3. 搜索并添加该应用（按应用名称）。
4. 授予「可编辑」权限。

否则会看到权限已开通、调用却返回无权限或找不到资源的情况。这一步必须做，且每张新表都要做一次。

#### 12.9.3 需要记录的两个 ID

| ID | 从哪里获取 |
| --- | --- |
| `app_token` | 多维表格 URL 中 `/base/` 之后的那一段 |
| `table_id` | 打开具体数据表后，URL 中 `table=` 之后的那一段 |

这两个值写入网关配置，不涉及密钥，可以放在普通配置文件里。

#### 12.9.4 网关会用到的接口能力

官方 Node SDK 已提供完整封装，不需要手工拼 HTTP：

| SDK 调用 | 用途 |
| --- | --- |
| `client.bitable.appTableRecord.create` | 新建任务记录 |
| `client.bitable.appTableRecord.update` | 更新单条记录状态 |
| `client.bitable.appTableRecord.batchUpdate` | 批量更新（推荐，省频率配额） |
| `client.bitable.appTableRecord.search` | 查询任务（如按状态筛选） |
| `client.bitable.appTableField.list` | 校验字段结构是否与预期一致 |

启动时建议先调一次 `appTableField.list`，比对字段是否齐全，缺失就明确报错，而不是等到写入时才失败。

#### 12.9.5 是否需要订阅表格变更事件

第一版**不需要**，也不建议。

当前设计是单向同步：编排层是唯一事实来源，表格只是它的投影。如果同时订阅表格变更事件，人手动改表就会与编排层状态互相覆盖，产生双向冲突。

如果后续希望人在表里直接操作（例如手动标记完成），需要额外设计冲突解决规则后再开启。

#### 12.9.6 频率限制与批量写

- 优先使用 `batchUpdate` 批量提交，减少请求数。
- 同一记录短时间内的多次变更在网关侧合并后写入。
- 写入失败按指数退避重试，连续失败触发系统告警并降级为卡片看板。
- 定期把已完成任务归档到另一张表，控制单表记录规模。

#### 12.9.7 用哪个应用开通

建议只为**一个**应用开通多维表格权限（可复用项目经理应用，或单独建一个系统应用）。六个角色机器人不需要该权限，它们只负责各自的消息回帖。

这样做的原因是最小权限：表格是系统状态，不是角色业务输出；一个写入方也避免并发覆盖。

#### 12.9.8 配置核对清单

- [ ] 已添加 `bitable:app` 权限
- [ ] 已创建版本并发布
- [ ] 已把应用加为目标多维表格的协作者（可编辑）
- [ ] 已记录 `app_token` 与 `table_id`
- [ ] 已建好主表字段与 Agent 状态表
- [ ] 已建好所需视图（分组、筛选）
- [ ] 用 `scripts/check-bitable.mjs` 验证权限与字段（只读 + `--write` 各跑一次）
- [ ] 网关启动时校验字段结构
- [ ] 写入走批量接口并做合并
- [ ] 降级方案（卡片看板）已验证

### 12.10 看板由谁维护

先说结论：**运行时看板的写入者是编排层程序，不是任何一个机器人 Agent。**

#### 12.10.1 为什么不该让 Agent 去写表

| 如果让 Agent 写 | 后果 |
| --- | --- |
| 加一次“更新表格”的模型调用 | 每次状态变更都多烧 token |
| 靠模型判断该写什么 | 可能写错、漏写、格式不一致 |
| 六个 Agent 各写自己那行 | 并发覆盖，同一任务的状态互相矛盾 |
| 表与真实状态脱节 | 看板变成“另一个说法”，失去可信度 |

看板是**系统状态的投影**，不是业务输出。编排层本来就持有任务表与依赖图，写入只是把已有数据同步出去，属于确定性操作，不需要智能。

#### 12.10.2 正确做法

```text
任务状态变更事件
   → 编排层内部状态更新（唯一事实来源）
   → 写队列合并
   → 批量写入多维表格
```

编排层在以下六个时刻写入：任务创建、开始执行、进入阻塞、进入待审批、完成、失败。除此之外不写。

#### 12.10.3 用哪个应用的凭据

| 方案 | 说明 |
| --- | --- |
| 复用项目经理应用 | 少建一个应用，PM 本身就是协调者角色，语义也成立 |
| 单独建系统应用 | 职责更清晰，权限隔离更好 |

第一版建议**复用项目经理应用**：它已经配好并发布，减少一次配置成本。等需要更严格的权限隔离时，再把看板写入拆到独立系统应用。

六个角色机器人不需要开通多维表格权限，它们只负责各自的消息回帖。

**但这里必须分清“给应用开权限”和“给 Agent 加工具”是两件事：**

```text
项目经理应用（一组 App ID / Secret）
  ├── 用途 A：Agent 会话
  │     接收 @消息、跑 Pi session、回复结果
  │     由模型驱动 ← 会消耗 token，行为不确定
  └── 用途 B：多维表格 API
        创建/更新任务记录
        由编排层程序直接调用 ← 确定性，零 token
```

两个用途共用同一组凭据，但一个是“模型在跑”，另一个是“程序在跑”。

因此结论是：**给项目经理应用开通 `bitable:app` 权限，但不要把多维表格的写入工具放进项目经理 Agent 的工具白名单。** 否则模型会在运行时自主决定写表，回到 12.10.1 列出的那些问题。

具体配置：

| 配置项 | 值 |
| --- | --- |
| 开通权限的应用 | 项目经理应用 |
| 权限标识 | `bitable:app` |
| 表格授权 | 把该应用加为目标多维表格的协作者（可编辑） |
| API 调用者 | 编排层程序，不经过模型 |
| 项目经理 Agent 工具白名单 | **不包含**多维表格工具 |

也就是说：项目经理应用有两个身份用途，Agent 那一半只负责对话与派发，写表那一半完全由程序承担。

#### 12.10.4 一次性搭建由谁做

建表和建视图是一次性工作，两种方式都可行：

| 方式 | 做法 | 适合 |
| --- | --- | --- |
| 人工创建 | 在飞书里手动建字段与视图 | 推荐，字段类型与视图配置最直观 |
| 托管创建 | 让项目经理机器人按模板生成表与字段 | 想省事、且接受少量返工 |

无论哪种方式，**搭完就固定下来**：后续由编排层按固定字段写入。字段结构变更属于配置变更，需要同步更新网关的字段校验（12.9.4），否则启动时就会报错。

#### 12.10.5 一个必须避免的做法

不要设计成“每个机器人更新自己负责的那一行”。那会同时引入并发覆盖、状态不一致和额外 token 开销三个问题。

正确的关系是：**Agent 只负责干活并回帖，编排层负责把状态写进表。**

### 12.11 在飞书创建看板表的操作步骤

#### 12.11.1 先选对类型

飞书有两种容易混淆的载体：

| 类型 | 是否有本设计需要的 API | 用途 |
| --- | --- | --- |
| **多维表格** | 有 | 本设计使用 |
| 电子表格 | 否 | 普通表格计算 |

必须选**多维表格**。如果建成了电子表格，后面所有接口都用不了。

#### 12.11.2 创建位置

推荐从项目群的云文档创建，这样群成员天然可见：

1. 打开项目群。
2. 群设置中找到「云文档」，或点击输入框上方的「+」→「云文档」→「新建」。
3. 选择「多维表格」。
4. 命名为 `MultyAgent 任务看板`。

也可以从飞书左侧「云文档」→「新建」→「多维表格」创建，之后再分享给群。

#### 12.11.3 主表字段

默认第一列的「文本」是索引列，直接改成 `task_id`，其余字段按下面添加：

| 字段名 | 飞书字段类型 |
| --- | --- |
| `task_id` | 文本（第一列） |
| `title` | 文本 |
| `parent_task_id` | 文本 |
| `agent` | 单选 |
| `stage` | 单选 |
| `status` | 单选 |
| `progress` | 数字 |
| `depends_on` | 文本 |
| `artifacts` | 文本 |
| `blocker` | 文本 |
| `owner_action` | 文本 |
| `started_at` | 日期 |
| `updated_at` | 日期 |
| `finished_at` | 日期 |
| `tokens` | 数字 |

#### 12.11.4 单选字段的选项值

选项值建议直接用系统内部标识，避免同步时再做中英映射：

| 字段 | 选项 |
| --- | --- |
| `agent` | `project-manager`、`architect`、`frontend-developer`、`backend-developer`、`tester`、`auditor` |
| `stage` | `received`、`planned`、`implementation`、`verification`、`audit`、`integration`、`summary` |
| `status` | `queued`、`running`、`blocked`、`awaiting_approval`、`completed`、`failed` |

显示成中文可以后续用字段的「选项显示名」调整，但存储值保持英文。

#### 12.11.5 第二张表：Agent 状态

在同一份多维表格里新增一张数据表，命名 `Agent 状态`：

| 字段名 | 类型 |
| --- | --- |
| `agent` | 单选（同上六个选项） |
| `state` | 单选：`idle`、`running`、`blocked` |
| `current_task` | 文本 |
| `today_completed` | 数字 |
| `today_tokens` | 数字 |

#### 12.11.6 视图

| 视图名 | 配置 |
| --- | --- |
| 全局看板 | 按 `status` 分组 |
| 按 Agent | 按 `agent` 分组 |
| 已完成 | 筛选 `status = completed`，按 `finished_at` 倒序 |
| 待处理 | 筛选 `owner_action` 不为空 |
| 需关注 | 筛选 `status = blocked` 或 `status = failed` |

#### 12.11.7 取两个 ID

打开多维表格后，浏览器地址形如：

```text
https://xxx.feishu.cn/base/<app_token>?table=<table_id>&view=<view_id>
```

| ID | 位置 |
| --- | --- |
| `app_token` | `/base/` 之后、`?` 之前的那一段 |
| `table_id` | `table=` 之后、`&` 之前的那一段 |

注意 `app_token` 是**整份多维表格**的标识，两张数据表共用同一个 `app_token`，各自的 `table_id` 不同。

#### 12.11.8 把应用加为协作者

1. 打开该多维表格。
2. 点击右上角「分享」。
3. 在协作者搜索框输入应用名称（如 `MultyAgent-项目经理`）。
4. 添加并授予「可编辑」权限。

若分享面板搜不到应用，可尝试文档右上角「更多」中的文档应用入口，或先确认该应用已发布且对企业内可用。

这一步做完，就可以用 12.9.8 的自检脚本验证了。

#### 12.11.9 创建不了多维表格怎么办

**首先明确：在哪里创建不影响设计。** 只要满足两个条件即可——类型是多维表格，且项目经理应用被加为协作者。项目群里建不了就换个入口建，再分享给群。

可尝试的创建入口，按成功率排序：

1. 飞书主界面左侧「云文档」→ 右上角「新建」→「多维表格」。
2. 主界面左上角「+」→「新建文档」→「多维表格」。
3. 已有的云文档文件夹内「新建」。
4. 桌面客户端（移动端入口常更受限）。

若以上都不可用，按下面排查：

| 现象 | 可能原因 | 验证方式 |
| --- | --- | --- |
| 完全没有「多维表格」这个选项 | 管理员在企业设置中关闭了多维表格 | 让管理员查看云文档相关开关 |
| 选项存在但置灰或点击报错 | 该账号或所在部门无创建权限 | 换一个有权限的账号试 |
| 群聊里找不到云文档入口 | 该群未启用云文档，或为外部群 | 在群设置中查看云文档开关 |
| 提示需要升级套餐 | 租户版本限制 | 让管理员确认版本能力 |

三条替代路径：

1. **请管理员创建**，并把编辑权限转交给你。
2. **复用已有的多维表格**，新建一张数据表即可，无需新建整份。
3. **走降级方案**：不建多维表格，改用 12.8.8 的群内卡片看板。任务流转不受影响，只是全局视图的体验差一些。

看板属于观测手段，不是流程的单点依赖。它暂时建不出来，不影响系统继续推进。

## 13. 审批

触发条件：策略标记为高风险的工具有调用请求时。

流程：策略扩展终止本轮 → 编排层创建审批记录 → 飞书发审批卡片（发起人 + 项目负责人）→ 批准后恢复该 session 继续执行 → 拒绝则记录原因并结束任务。

审批记录不可篡改，保留发起人、时间、工具、参数摘要与结论。

## 14. 可观测性与审计

三类日志分开存放：

| 类型 | 内容 | 用途 |
| --- | --- | --- |
| 任务日志 | 状态流转、耗时、错误 | 排障与进度 |
| 会话日志 | Pi 事件流原始记录 | 复盘 Agent 行为 |
| 审计日志 | 工具调用与策略结论 | 安全合规 |

日志不记录 `App Secret`、模型 API Key 和令牌。

## 15. 失败与恢复

- 事件重复：按 `message_id` 幂等，已处理直接忽略。
- Agent 超时：标记 `failed`，由对应机器人回帖失败原因，允许重试。
- 飞书发送失败：指数退避重试，超限后告警。
- 进程重启：session 文件持久化在 `runtime/sessions/`，任务恢复后可继续。
- 越权尝试：立即阻断并记录，不静默降级。

## 16. 安全边界与已知不足

诚实说明这套设计的边界：

1. 六个机器人在同一台机器、同一系统账户下运行。`bash`、`powershell` 一旦授予就没有系统级隔离。
2. 强制隔离依赖策略扩展的正确性。策略有漏洞，隔离就有漏洞。
3. 真正的强隔离需要容器或独立系统账户，属于第二阶段工作。
4. `pi-server` 目前的 Unix socket 传输不适用于 Windows，进程级桥接优先使用 SDK 或 `--mode rpc`。

## 17. 实施阶段

| 阶段 | 内容 | 产出 |
| --- | --- | --- |
| 一 | 建立六个 Profile、策略文件、工作区目录 | `.pi/agents/*.md`、`policy/*.yaml` |
| 二 | 实现 `pi-agent-policy` 扩展（拦截 + 注册工具 + 审计） | 可验证的越权阻断 |
| 三 | 实现 Pi 桥接层（SDK 或 RPC） | 网关能驱动单个 agent |
| 四 | 接入任务状态与产物管理 | 任务可查询、可恢复 |
| 五 | 接入编排层与跨 Agent 派发 | 跨角色协作可用 |
| 六 | 接入飞书审批卡片 | 高风险动作可审批 |
| 七 | 端到端演练与验收 | 完整链路证据 |

## 18. 验收标准

1. 每个机器人只使用自己的 Profile 与 session，上下文互不污染。
2. `@` 某机器人后，任务只进入该 Agent；结果由该机器人回帖。
3. 前端写入后端目录被阻断，且有审计记录。
4. 测试与审计无法修改业务代码。
5. 未授权工具调用被阻断，模型收到明确的拒绝原因。
6. 高风险动作进入审批，未批准不执行。
7. 前后端并行改代码不产生冲突。
8. 进程重启后未完成任务可恢复。
9. 冲突与失败都有可见反馈，不静默失败。
10. 日志中不出现任何密钥。

## 19. 端到端流程实例

场景：产品同学在飞书群里 `@项目经理`，提出“给后台加一个手机号登录”。

### 阶段 0：系统构成

```text
飞书项目群（六个机器人，各自独立 App）
        ↓
飞书接入层：长连接、去重、App ID → 角色映射（已建成）
        ↓
任务编排层：任务表、依赖图、上下文构造、审批、恢复
        ↓
Pi 运行时：六个独立进程，每个一根 stdin/stdout
        ↓
策略层：工具白名单、路径范围、风险拦截、审计
        ↓
工作区：主仓库 + 前后端各自 worktree + 产物仓库
```

### 阶段 1：接入与登记

1. 飞书把消息事件推给对应机器人的长连接。
2. 接入层按 `app_id` 识别出这是项目经理，校验群聊与发送人，按 `message_id` 去重。
3. 创建任务 `T-42`，立即回帖“已接收，正在处理”。
4. 状态：`received`。

### 阶段 2：项目计划

1. 编排层构造上下文：角色系统提示 + 用户原话 + 项目简述 + 策略边界（引用注入，不含历史对话）。
2. 向项目经理进程写 stdin：`{"type":"prompt","message":"任务 T-42：..."}`。
3. 项目经理产出 `requirements.md`（含可判定的验收标准）与 `plan.md`（含依赖图、责任分配）。
4. 调用 `deliver_artifact` 交付；编排层校验后状态转为 `planned`，由项目经理机器人回帖计划摘要。

### 阶段 3：架构与契约

1. 编排层按依赖图派发架构任务，注入 `requirements.md` 的引用。
2. 架构设计师产出 `architecture.md`、`contracts/api.yaml`、`contracts/data-model.sql`，并标记风险与假设。
3. 交付包校验通过，产物冻结到 commit；契约变更属于人审节点，向项目经理与发起人发确认卡片。
4. 确认后状态转为 `planned → queued`，契约版本即为后续实现锚点。

### 阶段 4：并行实现

1. 编排层判定前端与后端无写依赖，可并行，同时派发两个任务。
2. 各自在独立 worktree 中工作：`agent/frontend/T-42`、`agent/backend/T-42`。
3. 契约以 commit hash 锚定注入，两边都基于同一版实现。
4. 策略层拦截越权：前端写后端目录、后端改契约文件，都会被 block。
5. 全局并发闸门限制同时执行数，超出部分排队。

### 阶段 5：缺信息时的插入（关键环节）

1. 前端读契约发现缺少令牌过期时间的定义。
2. 前端不直接联系后端，而是调用 `request_input`。
3. 编排层先查产物仓库，确认无此定义。
4. 派发子任务给后端：补全契约字段。
5. 前端任务置为 `blocked`，不空转、不轮询。
6. 后端更新契约后，编排层唤醒前端：`{"type":"prompt","message":"契约已更新至 v4，请继续"}`。

这一步是整套设计最能体现“星型中介”价值的地方。

### 阶段 6：独立验证

1. 编排层派发测试任务，注入契约版本与前后端变更说明的引用。
2. 测试 Agent 使用独立 session，不继承开发者的结论。
3. 测试设计用例、执行、记录缺陷与复现步骤，产出 `test-report.md`。
4. 缺陷按类型回派对应 Owner；修完必须重跑，不允许带病进入下一环。

### 阶段 7：审计

1. 审计任务只读执行：代码质量、依赖、密钥、权限配置。
2. 产出 `audit-report.md`，发现按严重度排序，附文件与行。
3. 审计不修代码。需要修复时由编排层回派 Owner。
4. 高危发现阻塞流程，要求修复后复审。

### 阶段 8：集成与合并

1. 前后端分支在集成分支上合并，跑完整测试与构建（集成闸门）。
2. 合并顺序由依赖图决定；合并动作由编排层或人工执行，Agent 不自行合并。
3. 出现冲突时不自动解决，暂停分类，升级到对应 Owner 或人工裁决。
4. 全部通过后生成产物清单与变更摘要。

### 阶段 9：汇总与交付

1. 编排层把各产物引用交给项目经理。
2. 项目经理产出 `summary.md`，经项目经理机器人回帖飞书群。
3. 状态转为 `completed`；全过程的任务日志、会话日志、审计日志留存。
4. 发起人可在群里追问，追问复用 `T-42` 的会话；新需求开新任务。

### 贯穿全程的机制

| 机制 | 作用点 |
| --- | --- |
| 权限策略 `tool_call` 拦截 | 每次工具调用 |
| 产物版本与 digest 校验 | 每次读写产物 |
| 交接包 schema 校验 | 每次任务完成 |
| 预算与轮次上限 | 每个任务 |
| 人审节点 | 契约变更、高风险动作、范围变更、例外放行 |
| 静默失败检测 | 超时、空产物、缺证据、跳过测试 |
| 审计日志 | 每一个动作 |

### 一句话回顾

飞书负责入口与展示，编排层负责顺序与边界，Pi 负责推理与执行，产物仓库负责内容与版本，git 负责隔离与追溯。六者各守一段，缺任何一段质量都会失控。
