# MultyAgent 飞书多机器人协作设计

## 1. 目标

为 MultyAgent 的每个职责 Agent 配置一个独立的飞书应用机器人。所有机器人加入同一个项目群，成员可以通过 `@机器人` 发起任务，并由被调用的机器人返回执行结果。统一网关负责事件接收、身份识别、任务路由、结果发送、日志和失败处理。

## 2. 机器人角色

首批支持以下逻辑角色：

| 角色 ID | 机器人职责 |
| --- | --- |
| `project_manager` | 项目目标拆解、任务分配、进度汇总 |
| `product` | 需求澄清、需求规格和验收标准 |
| `architect` | 技术方案、模块边界和接口设计 |
| `developer` | 编码、修改代码和构建结果 |
| `tester` | 测试执行、缺陷记录和回归验证 |
| `reviewer` | 代码审查、安全和质量检查 |
| `documenter` | 文档生成、更新和发布说明 |
| `operator` | 部署、监控、告警和故障处理 |

角色清单必须配置化，后续可以增加角色而无需改动路由核心逻辑。

## 3. 总体架构

```text
飞书项目群
  |-- @产品机器人 / @开发机器人 / ...
  v
飞书事件回调接口
  v
MultyAgent-FEISHU 网关
  |-- 签名校验与去重
  |-- App ID -> Agent 角色映射
  |-- 指令解析与权限检查
  |-- Agent 调度器
  |-- 状态存储、日志、重试
  v
对应 MultyAgent Agent
  v
使用该 Agent 的飞书应用凭证回复项目群

统一 Webhook -> 网关级告警和系统通知
```

每个职责使用独立的飞书应用机器人身份，包括名称、头像、App ID 和 App Secret。机器人身份是结果发送的唯一依据，网关不得使用项目经理机器人代发其他 Agent 的业务结果。

## 4. 消息流程

### 4.1 用户发起任务

1. 用户在项目群中 `@` 某个 Agent 机器人并发送文本或支持的卡片指令。
2. 对应飞书应用的事件订阅接口将事件发送到网关。
3. 网关完成请求解密（如启用）、签名校验、事件重复检查和 URL 验证响应。
4. 网关依据 `app_id` 映射 Agent；同时解析发送人、群聊、消息 ID 和指令内容。
5. 网关检查该群聊和用户是否有调用该 Agent 的权限。
6. 网关在原消息线程或群聊中立即回复“已接收，正在处理”。
7. 调度器异步执行对应 Agent，并保存任务状态。
8. Agent 完成后，网关使用该 Agent 的飞书凭证发送最终结果；结果包含任务 ID、状态、摘要、详情链接（如有）和错误信息（如失败）。

### 4.2 系统主动通知

网关在 Agent 不可用、队列阻塞、部署失败或其他全局异常时调用配置的自定义机器人 Webhook。Webhook 仅用于系统级通知，默认不用于业务 Agent 结果，避免群聊中出现重复机器人身份。

### 4.3 长任务和失败

- 任务执行超过同步响应窗口时，必须先返回接收确认，再异步发送结果。
- 每个任务使用幂等任务 ID；重复事件不能重复执行。
- 飞书发送失败时按指数退避重试，超过上限后通过统一 Webhook 告警，并保留可人工重发的任务记录。
- Agent 执行失败时由对应机器人回复失败原因和下一步建议；禁止静默失败。

## 5. 配置模型

建议使用环境变量保存密钥，使用 YAML 或 JSON 保存非敏感角色配置。每个 Agent 至少包含：

```yaml
agents:
  developer:
    display_name: 开发机器人
    app_id: ${FEISHU_DEVELOPER_APP_ID}
    app_secret: ${FEISHU_DEVELOPER_APP_SECRET}
    agent_key: developer
    allowed_tools: [git, build]
    enabled: true
```

网关级配置包含事件回调地址、加密/校验参数、项目群 ID、Webhook 地址、重试策略、任务超时和日志级别。密钥不得写入仓库、日志或飞书消息。

## 6. 飞书权限与安全

每个应用只申请消息事件接收、读取必要群聊信息和发送消息所需的最小权限。高风险能力按角色隔离：例如运维机器人可以调用部署工具，开发机器人默认不能调用生产变更工具。

网关必须校验飞书请求签名或事件校验令牌，验证事件来源，限制允许的群聊和用户范围，并对消息内容和工具参数做输入校验。所有出站消息使用机器人自己的租户访问令牌，令牌只缓存在服务端并按过期时间刷新。

## 7. 可观测性

每次事件、调度和发送动作记录统一字段：`task_id`、`agent_key`、`app_id`、`chat_id`、`message_id`、状态、耗时和错误码。日志中不得记录 App Secret、访问令牌或完整敏感消息内容。

## 8. 验收标准

- 8 个机器人可以同时加入同一个项目群，并能被分别 `@`。
- `@` 某机器人后，任务只路由到对应 Agent。
- 接收确认和最终结果均由被调用的机器人发送。
- 重复飞书事件最多产生一个 Agent 任务。
- Agent 失败、飞书 API 失败和网关异常都有可见反馈及重试/告警。
- 未授权用户或非项目群请求会被拒绝且不触发 Agent。
- 敏感配置不出现在代码、日志和消息中。

## 9. 测试范围

- 单元测试：App ID 映射、指令解析、权限判断、签名校验、幂等去重、重试策略。
- 集成测试：飞书事件回调到 Agent 调度，再到对应机器人发送结果的完整链路。
- 故障测试：重复事件、过期令牌、飞书 API 超时、Agent 超时和 Webhook 不可用。
- 手工验收：在真实项目群中分别 `@` 每个机器人，确认名称、头像、回复身份和消息线程。
