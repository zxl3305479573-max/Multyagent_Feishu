# MultyAgent 飞书协作 · 项目总览

更新日期：2026-10-12
详细设计见 [Pi 多智能体架构设计](superpowers/specs/2026-09-14-pi-multiagent-feishu-architecture.md)

## 一、这个项目要做什么

在飞书项目群里，为六个职责角色各配一个独立机器人。成员 `@` 某个机器人提出任务，任务由该角色的 Agent 执行，结果由**同一个机器人**回到群里。复杂需求由多个角色分工协作完成。同一套网关也服务 Windows 桌面工作台，用户可以在桌面端按项目提交任务、观察执行轨迹、暂停/继续/终止任务。

一句话：**用飞书和桌面工作台当前台，用 Pi Agent 当工人，用编排层当调度，让六个角色像团队一样干活。**

## 二、系统分层

```text
飞书项目群（六个机器人）      桌面工作台（Electron，本机 WebSocket）
        ↓                              ↓
接入层       长连接 · 去重 · App ID → 角色映射 · 卡片回调 · 本机控制面
        ↓
编排层       TaskStore · 结构化计划 · 依赖就绪 · 人工确认 · 暂停检查点
        ↓
Agent 运行时  进程内 Pi 会话（默认）或 RPC 子进程，可选 Git worktree 隔离
        ↓
策略层       工具白名单 · 写入目录 · Shell 写入/内联脚本拦截 · 联网白名单
        ↓
工作区       workspace/<project>/{frontend,backend,artifacts}
        ↓
观测层       events.jsonl · 多维表格看板 · Trace 表 · 桌面执行时间线
```

## 三、一次任务的流转

### 简单任务（单角色，日常大多数）

```text
用户 @前端开发 修改登录页样式
  ① 接入层识别角色、去重、登记任务、回执“已接收”
  ② 编排层构造上下文（角色提示 + 任务 + 相关产物引用）
  ③ 派发给前端 Agent 的 Pi 会话
  ④ 执行：读代码、改文件、跑测试（每次工具调用都经过策略层）
  ⑤ 交付：交接包（结论 + 产物 + 证据 + 假设）
  ⑥ 前端机器人回帖结果
```

### 完整任务（多角色，跨模块或契约变更）

```text
用户 @项目经理 做一个手机号登录

项目经理    → 需求与验收标准，提交结构化阶段计划（assignments）
架构设计师  → 架构方案 + 接口契约（契约经人审确认后冻结）
前端开发 ┐
后端开发 ┴ → 同一阶段并行实现
测试       → 独立验证，产出测试报告
审计       → 只读检查，高危发现阻断流程
项目经理   → 汇总交付，回帖飞书群 / 桌面端
```

项目经理默认不派发下游角色，只有确实需要其他角色的专业能力时才在 `assignments` 中列出；计划中同阶段任务并行，阶段之间按依赖顺序推进。

**Agent 之间不说话，但消息在流动，每一跳都经过编排层。**

## 四、六个角色

角色定义统一在 `config/roles/<role>.json`（每个角色一个文件，启动时由 `src/role-config.cjs` 校验）。提示词中的“只能写入哪些目录、Shell 能做什么、能否联网”由同一份配置自动生成，与策略层实际拦截的规则保持一致。

| 机器人 | 职责 | 可写目录 | Shell |
| --- | --- | --- | --- |
| 项目经理 | 拆解需求、编排、汇总 | `workspace/{project}/artifacts` | 只读 |
| 架构设计师 | 架构方案、接口契约、技术风险 | `workspace/{project}/artifacts` | 只读 |
| 前端开发 | 页面、组件、交互 | `workspace/{project}/frontend`、`artifacts` | 可写（受目录限制） |
| 后端开发 | 接口、业务逻辑、数据模型 | `workspace/{project}/backend`、`artifacts` | 可写（受目录限制） |
| 测试 | 测试设计与执行、缺陷反馈 | `workspace/{project}/artifacts` | 只读 |
| 审计 | 代码质量、安全、依赖、权限 | `workspace/{project}/artifacts` | 无 |

## 五、关键机制

| 机制 | 作用 |
| --- | --- |
| 单一事实来源 | 任务状态只由 `src/domain/task-store.js` 的 `TaskStore` 持久化；看板、Trace、桌面端都是它与事件日志的投影 |
| 原子写盘 | 状态文件先写临时文件再改名（`src/atomic-file.cjs`）；文件损坏时备份为 `*.corrupt-<时间>` 并拒绝启动，不会被空状态覆盖 |
| 星型协作 | 所有跨 Agent 通信经编排层，不点对点直连 |
| 交接契约 | 每次交付必带结论、产物、证据、假设 |
| 最终汇总 | 项目经理发起的任务链，只有项目经理的 `final=true` 才算收尾；其他角色声明 `final` 仍会沿计划/路由交回项目经理汇总 |
| 三层边界 | 系统提示告知 + 任务信封声明 + 策略层强制拦截（`src/agent/policy-gate.js`） |
| Shell 写入校验 | 重定向、cp/mv/sed -i/Set-Content 等改写命令的目标必须在角色可写目录内；内联脚本（node -e、python -c、powershell -Command）一律拒绝 |
| git 隔离 | 可选 worktree 工作区，改动收集为补丁，人工确认后再合并 |
| 事件日志 | `runtime/events.jsonl` 只追加；桌面端补发与状态查询从文件尾部倒读；超过阈值时启动阶段归档，并保留进行中任务的事件 |
| 优雅退出 | 收到 Ctrl+C / SIGTERM / 桌面端 IPC 时依次关闭长连接、控制面、看板轮询，刷新任务快照，最后释放单实例锁 |

## 七、注意事项

1. **重置曾经暴露的 App Secret。** 项目经理与架构设计师的 Secret 曾在聊天中出现过；如果尚未在开放平台重置，请重置后更新桌面端凭据或 `.env`。
2. **Shell 静态校验不是沙箱。** 它能拦住越权写入和常见的删除/联网命令，但 `npm test` 这类命令本身会执行项目代码。需要强隔离时开启 `PI_AGENT_WORKTREE=1`，或在受限账户/容器中运行网关。

## 八、下一步建议

- 把任务状态从 JSON 文件迁移到 SQLite（Node 22 自带 `node:sqlite`），进一步降低写放大。
- 为结构化计划补充契约版本与所有者约束。
- 逐个模块开启 `// @ts-check`，扩大类型检查覆盖面。
