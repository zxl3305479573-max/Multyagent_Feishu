# 项目介绍（面向 HR）

生成日期：2026-09-15
适用岗位：AI 应用开发 / Agent 开发 / 平台工程（其他方向需调整措辞）

---

## 一、一句话定位

独立设计并落地了「飞书多机器人协作」项目：为六个职责角色各配一个独立飞书机器人，用户 `@` 任一机器人即可派活，任务由对应角色的 AI Agent 执行，结果由同一个机器人回到群里。

## 二、简历顶部摘要（可直接放项目经历首行）

> 面向团队协作场景的 AI Agent 项目。独立完成飞书开放平台六个自建应用的配置与接入，实现长连接事件订阅、消息幂等去重与按机器人身份路由回复，完成端到端消息闭环；并完成一套多智能体协作架构设计，覆盖角色分工、工具权限隔离、上下文管理与质量控制。

## 三、项目要点

**要点一：把六个职责角色做成六个真实身份**

- 动作：在飞书开放平台创建并发布六个自建应用，分别对应项目经理、架构设计师、前端开发、后端开发、测试、审计。
- 系统能力：基于官方 Node SDK 建立六条独立长连接，按 `App ID` 识别事件归属角色，做消息幂等去重与群聊校验。
- 业务价值：用户直接在群里 `@` 具体角色即可派活，不需要额外系统入口；每个职责有独立身份，责任边界在交互层就清晰可见。
- 结果证据：六个机器人全部连通；实际群消息触发完整闭环，日志记录任务号、群 ID、消息 ID 与状态。
- 个人边界：接入层为本人独立实现；消息处理逻辑当前为占位实现，真实 Agent 执行待接入。

**要点二：完成多智能体协作架构设计**

- 动作：设计六个独立 Agent 的协作模型，包含角色分工、协作拓扑、依赖管理、交接契约与质量门禁。
- 系统能力：确立「星型中介」协作拓扑——Agent 之间不直接通信，全部经编排层转发，以保证权限可校验、身份不错乱、过程可审计、任务可恢复。
- 业务价值：解决了多 Agent 系统最容易失控的三个问题——谁在指挥、谁对结果负责、出了问题怎么定位。
- 结果证据：形成 20 章设计文档，含权限矩阵、工具清单、状态机、端到端流程实例与验收标准。
- 个人边界：架构为设计产出，尚未全量实施。

**要点三：技术选型与取舍判断**

- 动作：调研并对比主流多智能体框架后做出技术选型决策。
- 系统能力：对比 AutoGen、CrewAI、LangGraph 与本地方案后，决定基于 Pi Agent 自建轻量编排层，不引入重型框架；并从机制上论证了「跨角色不能用子 Agent 实现」——子 Agent 的权限上限受父会话继承、生命周期绑定父会话、产出由父 Agent 汇报，与「谁执行谁回帖」的要求冲突。
- 业务价值：避免过早引入重型框架带来的复杂度，同时保证后续可替换运行时。
- 结果证据：GitHub 一手数据（AutoGen 约 6.1 万星、CrewAI 约 5.8 万星、LangGraph 约 4.2 万星）与本地 Pi 扩展能力核对记录。
- 个人边界：选型分析与论证由本人完成。

**要点四：权限与质量控制机制设计**

- 动作：设计三层权限模型与独立验证机制。
- 系统能力：工具白名单 + 任务信封声明 + 策略层在工具调用前强制拦截；前后端分工作区、契约用 commit 锚定版本；测试不复用开发者结论、审计全程只读。
- 业务价值：把「不越界」从提示词约定升级为机制约束，同时保证质量检查的独立性。
- 结果证据：设计文档中给出权限矩阵、冲突分类与防护对照、质量门禁顺序与静默失败清单。
- 个人边界：设计产出，未实施；实施需落地策略扩展。

## 七、可能被追问的问题

1. 六个机器人为什么不做成一个机器人分角色？（答案：身份归属与权限隔离）
2. Agent 之间怎么通信，为什么不让它们直接对话？（答案：星型中介，路由权与权限校验）
3. 多个 Agent 并行怎么避免冲突？（答案：worktree、契约版本锚定、单一所有者、集成闸门）
4. 怎么防止 Agent 越权？（答案：三层边界，策略层强制拦截）
5. 怎么保证 AI 的产出质量？（答案：独立验证、可复现证据、静默失败按失败处理）
6. Token 成本怎么控制？（答案：轮次是主因，任务分级 + 引用注入 + 确定性工具替代）
7. 这套东西最难的判断是什么？（答案：跨角色不能用子 Agent，以及为什么）
